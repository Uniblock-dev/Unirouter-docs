Every request to the public API is authenticated by one API key on one header. There is no other
credential, no session, and no signature: a key opens the door and nothing else does.

## How to

### Send a key

<AuthHeader />

<CodeGroup>

```bash curl
curl https://api.hopscotchlabs.ai/v1/chat/completions \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{"model": "openai/gpt-4o-mini", "messages": [{"role": "user", "content": "Hello."}]}'
```

```python Python
from openai import OpenAI

# The SDK puts the key on the Authorization header for you.
client = OpenAI(
    base_url="https://api.hopscotchlabs.ai/v1",
    api_key="ub_live_YOUR_KEY_HERE",
)
```

```javascript Node
import OpenAI from "openai";

// The SDK puts the key on the Authorization header for you.
const client = new OpenAI({
  baseURL: "https://api.hopscotchlabs.ai/v1",
  apiKey: "ub_live_YOUR_KEY_HERE",
});
```

</CodeGroup>

The scheme must be `Bearer`. A missing header and a header using another scheme get the same refusal,
because from our side both mean no key arrived.

### Create a key

Keys are created in the dashboard, on the **Keys** screen, never through the API.

**Who can do this:** owner, admin or developer. A viewer is refused with `Your role in this workspace
cannot create API keys.` See [Workspaces and members](/manage/workspaces-and-members).

<Steps>
  <Step title="Open Keys in the dashboard">
    Sign in and go to Keys. The screen lists the keys you may see, which is not always every key in the
    workspace. See [Who can see which keys](#who-can-see-which-keys).
  </Step>
  <Step title="Name it">
    Name the key for where it will be used, such as `production-api` or `ci`. The name is how you recognise
    it later, because the secret is not shown again.
  </Step>
  <Step title="Create it, and copy it now">
    The key is shown once, in full, in the form `ub_live_` followed by 43 characters, and nowhere else. Put
    it straight into your secret manager or your deployment's environment. Copying it into a note to paste later
    is the handling the once-only showing exists to discourage.
  </Step>
  <Step title="Use it">
    Send it as a bearer token, as shown under [Send a key](#send-a-key).
  </Step>
</Steps>

### Set an expiry and a spending limit

Both are optional, and both are set on the key when you create it or later from its row. A key with neither
never expires and spends against the workspace balance with no ceiling of its own.

**Expiration** is a date. A key presented after it is refused with code `key_expired`, and the refusal names
the instant it expired. Nothing renews an expired key: the fix is a new key.

**Credit limit** is an amount this key may spend, with a **Reset** cadence beside it: never, daily, weekly or
monthly, on UTC calendar windows. A request that would take the key past its limit is refused with code
`key_limit_exceeded` before anything is held or charged. The refusal names what the key has settled and holds
in its current window. Other keys in the workspace keep serving from the same balance.

The cadence is available only once there is a limit for it to apply to. Emptying the amount returns the cadence
to never, and a limit that never resets does not clear by waiting: raise it or remove it. See
[Spend controls](/manage/spend-controls).

### End a key

Three things can end a key, and nothing else does. Ending a key means it stops existing and its slot frees.

| Reason | What causes it | Available today |
|---|---|---|
| You revoke it | Somebody with access ends that key deliberately. | Yes |
| It was replaced | Minting a replacement ends the key it replaces in the same motion. | Yes |
| A member was removed and the person removing them chose to revoke that key | Removal asks about each key rather than deciding for you. | Yes |

**Revoke** asks "Stop this key from working?" and ends the key on **Revoke it**. Nothing replaces it. **Regenerate**
asks "Replace this key with a fresh one? The old one stops working." and, on **Regenerate it**, ends the old key and
shows the new one once, the way a new key is shown. The old key is confirmed ended before the new one is shown, so
you are never told a key was replaced while it still works somewhere. Regenerating needs the permission to create a
key as well as the permission to revoke one. Both are offered to anyone who may revoke that key: an owner, an admin,
or the developer it is accountable to.

Revoking and regenerating share an account-wide churn allowance. Past it, the response is HTTP 429 with the code
`too_many_key_operations` and a `Retry-After` header, until the window passes.

Expiry is a fourth way a key **stops serving traffic**, but it does not end the key: an expired key still holds its
slot until it is revoked or replaced, and only a new key restores traffic.

A role change never revokes a key, and neither does a workspace pause: lifting a pause needs no new key.

Hopscotch staff can also revoke a key, recorded against a named member of staff. We publish no figure for how quickly
that takes effect everywhere.

## The key format

A key is a non-secret prefix followed by 43 random characters from the base64url alphabet: `A-Z`, `a-z`, `0-9`, `-`
and `_`.

| Prefix | Environment |
|---|---|
| `ub_live_` | Production. This is the one you get from the dashboard. |
| `ub_stg_` | Staging. |
| `ub_dev_` | Development. |

The prefix lets secret scanners recognise a leaked Hopscotch key in a public repository, and says which environment a
misplaced key belongs to. The prefix and the last four characters stay visible in the dashboard, so you can tell keys
apart; the other 39 characters are gone from our side once shown.

We keep only a hash, so a key cannot be shown again or recovered. That is a property of the design: a leak of our
database yields no working key, and the same fact stops us reading yours back. If you lose a key, mint a new one and
end the lost one, as described under [End a key](#end-a-key).

## Keys belong to the workspace

A key belongs to the workspace, not to the person who minted it. Its spend lands on the workspace balance and its
requests land in the workspace usage. Removing the member who created a key does not stop it on its own; revoking is
a per-key choice made at the moment of removal. See [workspaces and members](/manage/workspaces-and-members).

Each key has one accountable member, which says who answers for its spend. Accountability is not a permission: it does
not say who may use the key.

## 500 live keys per workspace

A workspace holds up to 500 live keys. A request for one more at 500 is refused with: `This workspace already holds 500
live keys, which is the maximum. Revoke one to free a slot.`

The ceiling counts live keys, not keys ever minted, so an ended key frees its slot. Several keys rather than one is
deliberate: with one, a leak means an outage. With several, you can create the replacement, move traffic, and end the
old key with nothing down in between.

### Keys that arrive with an invitation

An invitation can carry a key reservation, so a new member arrives with a key waiting for them.

- The reservation takes one of the 500 slots as soon as it is made, though the key does not exist yet. The key is
  created once, the first time the invitee views it after accepting.
- It is shown once, with the same sentence as any new key. If two tabs press the button together, exactly one key is
  created, and the other tab is told the key was already shown, with its prefix and last four characters. There is no
  second showing.
- A reservation lapses and frees its slot if the invitation is never accepted, or if seven days pass after acceptance
  without the key being viewed. An owner or admin can cancel an unviewed reservation. A lapse or cancellation is not a
  revocation, because the key never existed.

## Who can see which keys

Every key list carries this sentence:

> Key lists are scoped to what each member may see. An owner or admin sees every key in the workspace; everybody
> else sees the keys they are accountable for or named on.

When creating a key, an owner or an admin can limit it to named members. That limit decides who can see and manage the
key, and nobody outside the list learns that it exists. A developer or viewer who tries to set a limit is refused with:
`Only an owner or an admin can limit a key to particular members.`

The limit does not change what the key can do: on the request path a key is a bearer credential, so anybody holding the
secret can call the API with it. The limit covers screens and management, not a per-person usage split.

## Refusals

Refusals arrive in the OpenAI error envelope, so an OpenAI client parses them without changes.

<ErrorEnvelope />

All four carry `"type": "authentication_error"`. The first three share `"code": "invalid_api_key"`. The fourth carries
`key_expired` because the fix differs: an expired key was valid and needs replacing. Branch on `code`, never on the
message. Every shipped code is in [Errors and refusals](/api-reference/errors).

| What happened | The message |
|---|---|
| No `Authorization` header, or a scheme other than `Bearer` | `You did not provide an API key. Send it in an Authorization header using Bearer auth.` |
| A string that is not shaped like a Hopscotch key | `Incorrect API key format. A Hopscotch key looks like ub_live_ followed by 43 characters. Check you have not pasted a key from another provider.` |
| A correctly shaped key we do not accept | `Incorrect API key provided.` |
| A key past its own expiry date (`code: key_expired`) | Names the instant the key expired on. Checked before the per-key rate limiter, so an expired key never consumes that allowance. |

The second row is separate from the third on purpose: a key of the wrong shape is usually another provider's key or a
truncated paste. The third covers both a key that never existed and one that was revoked, with one identical sentence,
so confirming that a stolen key was once real helps only the thief.

A key carries a request rate limit, checked as the key is authenticated. Over it, the response is 429 with type
`rate_limit_error`, code `rate_limit_exceeded`, and a `Retry-After` header in seconds. That limit is ours to set and you
cannot raise it. Your account spend rate cap is a different refusal, with its own codes, which you can raise. See
[Spend controls](/manage/spend-controls).

## Handling keys well

- Keep keys in a secret store or an environment variable, never in source control. The `ub_live_` prefix lets scanners
  catch a leak, but catching it after the fact is not avoiding it.
- Use one key per deployment or service, within the 500 live keys ceiling, so ending one key costs one deployment, not
  all of them.
- We set no expiry on a key and publish no rotation requirement, so a key stays live until something above ends it. You
  may give a key an expiry date of your own.
