If your application already calls OpenAI, almost all of it survives the move. "OpenAI-compatible"
here means three specific things:

1. The request and response bodies are OpenAI's, and travel unchanged but for two rewrites named below.
2. Errors arrive in the OpenAI error envelope, so your existing error handling parses them.
3. What we add is additive: extra response headers and one SSE comment line, both of which a compliant
   client ignores.

## The two settings

<BaseUrl />

Your client keeps its own name for these. Change the base URL and change the key, and leave the rest of
your client configuration where it is.

<CodeGroup>

```python Python
from openai import OpenAI

client = OpenAI(
    base_url="https://api.hopscotchlabs.ai/v1",   # was: unset, or the OpenAI default
    api_key="ub_live_YOUR_KEY_HERE",         # was: your OpenAI key
)
```

```javascript Node
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "https://api.hopscotchlabs.ai/v1",  // was: unset, or the OpenAI default
  apiKey: "ub_live_YOUR_KEY_HERE",        // was: your OpenAI key
});
```

</CodeGroup>

## The endpoints that exist today

| Endpoint | Method | Status |
|---|---|---|
| `/v1/chat/completions` | `POST` | Serves. Streaming and non-streaming. |
| `/v1/responses` | `POST` | Serves. Streaming and non-streaming. See [Responses API](/features/responses-api). |
| `/v1/completions` | `POST` | Serves. Streaming and non-streaming. See [Completions and embeddings](/features/completions-and-embeddings). |
| `/v1/messages` | `POST` | Serves the Anthropic Messages format. See [Anthropic Messages API](/features/anthropic-messages). |
| `/v1/models` | `GET` | Serves. |
| `/v1/models/{id}` | `GET` | Serves. |
| `/v1/usage/{id}` | `GET` | Serves. See [Usage lookup](/features/usage-lookup). |
| `/v1/videos` | `POST` | Serves. Creates a video job. See [Videos](/features/videos). |
| `/v1/videos/{id}` | `GET`, `DELETE` | Serves. Reads or cancels a job. See [Videos](/features/videos). |
| `/v1/videos/{id}/content` | `GET` | Serves. Streams a finished video. See [Videos](/features/videos). |

The table lists the paths this site publishes. Other paths, including the image and audio endpoints,
`POST /v1/embeddings`, `POST /v1/systemone` and the realtime endpoint, are not documented on this site, so
treat any call to them as unanswered here. A path this release does not serve answers the 404 below.

### What a call to a path we do not serve returns

A path under `/v1` that this release does not serve is refused at one boundary, so it fails the same way
every time. It is a 404 in the OpenAI envelope, with type `invalid_request_error` and code
`endpoint_not_supported`. A method we do not serve on a path we do is a `405` with the code
`method_not_allowed` and an `Allow` header naming the methods that are served. A `GET` on
`/v1/chat/completions` is the everyday example.

## Model ids

Models are named `provider/model`, for example `openai/gpt-4o-mini`. The id is split once on the first
slash: the part before it names the provider that will serve the request, and everything after it is our name
for that model on that provider. The provider is still sent its own spelling, by us and not by you. The same
model carried by two providers is two ids, and you choose which one you send.

Every model id gains a provider in front of it. This is the one change that is not optional, and it breaks
loudly rather than quietly. A bare OpenAI-style name such as `gpt-4o-mini` is not a Hopscotch model id. It is
refused with `400` and the code `model_id_not_pinned`, naming both accepted forms. That refusal is deliberate:
a bare id would have to be resolved to some provider we happen to carry it under, and picking one for you is a
decision about price and about who sees your prompt that we are not willing to make on your behalf.

Find the ids you can call with `GET /v1/models`, or on the Models screen in the dashboard. Do not assemble them
by hand from a provider's own naming. See [Models](/features/models).

```bash
curl https://api.hopscotchlabs.ai/v1/models \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE"
```

## Request bodies and parameters

The chat completion body is forwarded as you sent it. There is no request schema of ours in front of it and no
allowlist of parameters, so a parameter your client already sends works without waiting for us to add it. A body
the provider rejects comes back as the provider's own OpenAI-shaped error. `max_tokens`, `temperature`, `tools`,
`response_format`, and the rest travel in the body.

Two fields are read on the way through, both to work out what the request could cost before it is sent: `model`,
and `max_tokens` or `max_completion_tokens`. Reading one does not change it.

Two rewrites exist, and they are the whole list. A request naming a routing profile or `unirouter/auto` has its
`model` replaced with the model being tried on that attempt, because that is what a route means. And a request
that names no output ceiling, sent to a provider whose own API refuses a request without one, has `max_tokens`
filled in with the model's published maximum output, which is the figure credit was already being held against.
Every other provider is sent your body without the field. [Request parameters](/api-reference/parameters) covers
both in full.

Nothing Hopscotch-specific belongs in a request. There is no parameter of ours to send, and no header can change how
a request is served.

**`max_tokens` is worth sending even though it is optional.** It is what sizes the amount we hold against your
balance before the call, so a request without it is held at the model's published maximum output and reaches your
account spend rate cap sooner. See [Spend controls](/manage/spend-controls).

## Request headers

Send `Authorization` and `Content-Type`. Nothing else you send is forwarded: the request we make on your behalf is
built from your request body and our own provider credential, with a fresh header set. Organisation and project
headers do not travel.

`x-uniblock-*` is our reserved namespace on both directions of the wire. Sending one has no effect for the same
reason: it does not travel.

## Response differences

All of these are additions to an otherwise unchanged OpenAI response.

**The request id.** Every response, success or error, carries `x-hopscotch-request-id`, and the same value on
`x-request-id`, which is the header the OpenAI SDKs already read. On an error, the id also appears as `request_id`
inside the `error` object. That fifth field inside `error` is the one shape difference from OpenAI's envelope, and
it is inside `error` rather than beside it precisely so that an SDK reading the fields it knows ignores it safely.

**Diagnostic headers.** A short allowlist describes how the request was served:

| Header | What it says |
|---|---|
| `x-hopscotch-provider` | Which provider family answered. |
| `x-hopscotch-retry-attempt-count` | How many attempts it took, so a slow success has a visible reason. |
| `x-hopscotch-cache-status` | Whether the reply came from cache rather than from the provider. |
| `x-hopscotch-trace-id` | A second internal id, distinct from your request id. |
| `x-hopscotch-served-by` | The full id, `{provider}/{model}`, of the model that actually answered. |

Each of these, and the request id above, was also sent under an `x-uniblock-` name until 2026-09-14. That spelling
was retired and is no longer written, so read the `x-hopscotch-` name, or `x-request-id` for the id. See
[Headers](/api-reference/headers).

**Provider rate-limit headers are not forwarded.** Nothing else the provider sets travels onward. If you currently
read the remaining-requests and reset headers that a provider sets, those are absent here, because they describe a
pool we hold rather than a limit that applies to you. Your own limits arrive as 429 responses with codes you can
branch on, documented in [Spend controls](/manage/spend-controls).

**One extra line on a stream.** A streamed reply carries one extra line immediately before `data: [DONE]`, starting
with a colon:

```text
:x-hopscotch-usage {"v":1,...}
```

The SSE specification requires a parser to ignore a line starting with a colon, so the OpenAI SDKs skip it and a
conforming client never sees it. [Streaming](/features/streaming) documents its fields. A non-streamed reply carries
no equivalent header today. The counts are read on our side and become your usage record.

**One extra field in an error.** The error object carries `request_id` alongside the fields OpenAI defines. It is
inside `error` rather than beside it so that a client reading only the fields it knows ignores it safely.

## Errors and billing

Status codes and the closed set of `type` values are OpenAI's. Branch on `type` and `code`, never on the message text:
the fields are the contract and the sentences are prose that may be reworded. Every shipped code and its status is in
[Errors and refusals](/api-reference/errors).

Some of our refusals are about billing rather than about your request: not enough credit, or an account spend rate cap.
Those reuse OpenAI's own `insufficient_quota` and `rate_limit_error` types, so the branch your client already has keeps
working, and carry a Hopscotch `code` that says which of them happened.

**Billing.** Credit is prepaid and the platform fee is added when you buy credit, not when you spend it, so a request
deducts the provider's own rate with nothing on top. A zero balance refuses new requests with `402` and ends in-flight
ones. See [Credits and billing](/manage/credits-and-billing).

## How to

<Steps>
  <Step title="Prefix every model id">
    Search your code for model names and put the provider in front of each one. This is the step that fails the
    first request if you skip it.
  </Step>
  <Step title="Point the client at the base URL and swap the key">
    Two settings, both above. Keep the key in the environment rather than in source.
  </Step>
  <Step title="Find any call to an endpoint this site does not document">
    Anything beyond the table above is undocumented here. Decide what those call sites do before you cut over
    rather than after, and treat them as unanswered rather than as either working or refused.
  </Step>
  <Step title="Stop reading provider rate-limit headers">
    If your pacing depends on them, move it onto `429` codes and `Retry-After`.
  </Step>
  <Step title="Send max_tokens">
    Especially on any call path that currently omits it.
  </Step>
  <Step title="Log the request id">
    `x-request-id` is the header the official SDKs already surface on their error objects, so this is usually a
    one-line change. Without it, a support conversation starts from a description rather than from a request.
  </Step>
  <Step title="Buy credit before you cut over">
    A verified account with a zero balance refuses every request, which is a confusing first result if you were not
    expecting it.
  </Step>
</Steps>

## What we do not claim

- We have not yet published a proof run of an unmodified official SDK against the production hostname. The
  instructions on this page set only `base_url` and `api_key`, which is the whole intended change. Read this page as
  instructions rather than as a certification, and we will say so as a tested result once that run exists.
- We make no statement here about behaviour under concurrency, latency added by the hop, throughput, or availability.
  No figure for any of those has been measured in a way we are willing to publish.
- Moving from another router is not documented here. The differences that matter would be differences from that
  product's behaviour, and we do not document other people's products from the outside.
