If your app already calls OpenAI, most of your code stays the same. When we say "OpenAI-compatible," we mean three things:

1. Request and response bodies use OpenAI's format. We pass them through as they are, apart from two rewrites covered below.
2. Errors come back in OpenAI's error format, so your existing error handling can read them.
3. Anything we add sits on top: a few extra response headers and one extra line at the end of a stream. Standard clients ignore both.

## The two settings

<BaseUrl />

Your client may use a different name for these settings, such as `base_url`, `baseURL` or `OPENAI_BASE_URL`. Update the base URL and the API key, and leave the rest of your client config alone.

<CodeGroup>

```python Python
from openai import OpenAI

client = OpenAI(
    base_url="https://api.hopscotchlabs.ai/v1",   # was: unset, or the OpenAI default
    api_key="ub_live_YOUR_KEY_HERE",         # was: your OpenAI key
)
```

```javascript Node
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "https://api.hopscotchlabs.ai/v1",  // was: unset, or the OpenAI default
  apiKey: "ub_live_YOUR_KEY_HERE",        // was: your OpenAI key
});
```

</CodeGroup>

## The endpoints that exist today

| Endpoint | Method | Status |
|---|---|---|
| `/v1/chat/completions` | `POST` | Serves. Streaming and non-streaming. |
| `/v1/responses` | `POST` | Serves. Streaming and non-streaming. See [Responses API](/features/responses-api). |
| `/v1/completions` | `POST` | Serves. Streaming and non-streaming. See [Completions and embeddings](/features/completions-and-embeddings). |
| `/v1/messages` | `POST` | Serves the Anthropic Messages format. See [Anthropic Messages API](/features/anthropic-messages). |
| `/v1/models` | `GET` | Serves. |
| `/v1/models/{id}` | `GET` | Serves. |
| `/v1/usage/{id}` | `GET` | Serves. See [Usage lookup](/features/usage-lookup). |
| `/v1/videos` | `POST` | Serves. Creates a video job. See [Videos](/features/videos). |
| `/v1/videos/{id}` | `GET`, `DELETE` | Serves. Reads or cancels a job. See [Videos](/features/videos). |
| `/v1/videos/{id}/content` | `GET` | Serves. Streams a finished video. See [Videos](/features/videos). |

The table lists the paths this site publishes. Other paths, including the image and audio endpoints,
`POST /v1/embeddings`, `POST /v1/systemone` and the realtime endpoint, are not documented on this site, so
treat any call to them as unanswered here. A path this release does not serve answers the 404 below.

### What a call to a path we do not serve returns

A path under `/v1` that this release does not serve is refused at one boundary, so it fails the same way
every time. It is a 404 in the OpenAI envelope, with type `invalid_request_error` and code
`endpoint_not_supported`. A method we do not serve on a path we do is a `405` with the code
`method_not_allowed` and an `Allow` header naming the methods that are served. A `GET` on
`/v1/chat/completions` is the everyday example.

## Model ids

Model ids use the format `provider/model`, for example `openai/gpt-4o-mini`. We split the id at the first slash. The part before the slash is the provider that serves the request. The part after it is our name for that model on that provider. When we call the provider, we use the provider's own name for the model, so you never need to know it.

If two providers offer the same model, that model has two ids, and you pick which one to call.

**Add a provider to every model id.** It's the only change you can't skip, and if you miss it you'll find out on your first request. A bare OpenAI name like `gpt-4o-mini` returns a `400` with the code `model_id_not_pinned`, and the error message shows both formats we accept.

We refuse bare ids on purpose. To serve one, we'd have to pick a provider for you. That choice affects what you pay and who sees your prompts, so we leave it to you.

To find the ids you can call, use `GET /v1/models` or the Models screen in the dashboard. Copy ids from there instead of building them from a provider's own model names. See [Models](/features/models).

```bash
curl https://api.hopscotchlabs.ai/v1/models \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE"
```

## Request bodies and parameters

We forward your chat completion body exactly as you send it. We don't check it against a schema of our own or limit which parameters you can use, so anything your client sends today keeps working. `max_tokens`, `temperature`, `tools`, `response_format` and everything else go in the body as usual. If the provider rejects your body, you get the provider's own error in OpenAI's format.

We read two fields on the way through so we can estimate the cost before sending the request: `model`, and `max_tokens` (or `max_completion_tokens`). Reading them doesn't change them.

There are only two cases where we change your request:

- **Routing.** If you call a routing profile or `hopscotch/auto`, we replace `model` with the model we're trying on that attempt. That's how routing works.
- **Missing output limit.** Some providers refuse any request that doesn't set a maximum output. If you send one of these providers a request without `max_tokens`, we fill it in with the model's published maximum output. That's the same number we already used to hold credit for the request. For every other provider, we leave `max_tokens` unset.

[Request parameters](/api-reference/parameters) covers both cases in detail.

You don't need to add anything Hopscotch-specific to your requests. We have no custom parameters, and no header changes how we serve a request.

**Send `max_tokens` even though it's optional.** Before each call, we hold part of your balance to cover it, and `max_tokens` sets how much. Without it, we hold enough for the model's maximum output, so you'll hit your spend rate cap sooner. See [Spend controls](/manage/spend-controls).

## Request headers

Send `Authorization` and `Content-Type`. We don't forward any other headers. When we call the provider, we build a new request from your body and our own provider credential, with a fresh set of headers. That means OpenAI's organization and project headers (`OpenAI-Organization` and `OpenAI-Project`) are dropped.

We reserve `x-hopscotch-*` for our own headers in both directions. If you send one, we drop it like any other header, so it has no effect.

## Response differences

Except for the provider rate-limit headers covered below, everything in this section is added to a standard OpenAI response.

**Request id.** Every response, success or error, includes `x-hopscotch-request-id`. We send the same value as `x-request-id`, which the OpenAI SDKs already read. On errors, it also appears as `request_id` inside the `error` object.

**Diagnostic headers.** These show how we handled the request:

| Header | What it tells you |
| --- | --- |
| `x-hopscotch-provider` | The provider that answered. |
| `x-hopscotch-retry-attempt-count` | How many attempts the request took. Useful when a request succeeds but runs slower than expected. |
| `x-hopscotch-cache-status` | Whether the reply came from our cache instead of the provider. |
| `x-hopscotch-trace-id` | A second internal id, separate from your request id. |
| `x-hopscotch-served-by` | The full `{provider}/{model}` id of the model that answered. |

Until 2026-09-14, we also sent each of these headers, and the request id, under an `x-uniblock-` name. We no longer send those, so read the `x-hopscotch-` version, or `x-request-id` for the request id. See [Headers](/api-reference/headers).

**Provider rate-limit headers.** We don't pass on any other headers from the provider. If your app reads headers like remaining requests or reset time, they won't be there. Those numbers describe the capacity we share across all customers, so they wouldn't tell you anything about your own limits. When you hit one of your own limits, you get a `429` with a code you can check. See [Spend controls](https://docs.hopscotchlabs.ai/manage/spend-controls.md).

**An extra line in streams.** Right before `data: [DONE]`, a streamed reply includes one extra line that starts with a colon:

```text
:x-hopscotch-usage {"v":1,...}
```

The SSE spec tells parsers to ignore lines that start with a colon, so the OpenAI SDKs skip it and your code never sees it. [Streaming](/features/streaming) lists its fields. Non-streamed replies don't have an equivalent yet. In both cases, we count tokens on our side, and those counts become your usage record.

**An extra field in errors.** Error objects include `request_id` next to OpenAI's standard fields. It's the only difference from OpenAI's error format. We put it inside `error` so that clients reading only the fields they know will skip it.

## Errors and billing

Status codes and `type` values match OpenAI's. In your error handling, check `type` and `code` and don't match on the message text, because we may reword it. [Errors and refusals](/api-reference/errors) list every code and its status.

Some refusals are about your account instead of your request, like running out of credit or hitting your spend rate cap. These use OpenAI's existing `insufficient_quota` and `rate_limit_error` types, so your current error handling still catches them. Each one also includes a Hopscotch `code` that tells you exactly what happened.

**Billing.** Credit is prepaid. We charge our platform fee when you buy credit, so each request costs exactly the provider's rate with nothing added. If your balance reaches zero, new requests get a `402` and any requests still running are stopped. See [Credits and billing](/manage/credits-and-billing).

## Migration steps

<Steps>
  <Step title="Prefix every model id">
    Search your code for model names and put the provider in front of each one. This is the step that fails the
    first request if you skip it.
  </Step>
  <Step title="Point the client at the base URL and swap the key">
    Two settings, both above. Keep the key in the environment rather than in source.
  </Step>
  <Step title="Find any call to an endpoint this site does not document">
    Anything beyond the table above is undocumented here. Decide what those call sites do before you cut over
    rather than after, and treat them as unanswered rather than as either working or refused.
  </Step>
  <Step title="Stop reading provider rate-limit headers">
    If your pacing depends on them, move it onto `429` codes and `Retry-After`.
  </Step>
  <Step title="Send max_tokens">
    Especially on any call path that currently omits it.
  </Step>
  <Step title="Log the request id">
    `x-request-id` is the header the official SDKs already surface on their error objects, so this is usually a
    one-line change. Without it, a support conversation starts from a description rather than from a request.
  </Step>
  <Step title="Buy credit before you cut over">
    A verified account with a zero balance refuses every request, which is a confusing first result if you were not
    expecting it.
  </Step>
</Steps>

## What we do not claim

- We have not yet published a proof run of an unmodified official SDK against the production hostname. The
  instructions on this page set only `base_url` and `api_key`, which is the whole intended change. Read this page as
  instructions rather than as a certification, and we will say so as a tested result once that run exists.
- We make no statement here about behaviour under concurrency, latency added by the hop, throughput, or availability.
  No figure for any of those has been measured in a way we are willing to publish.
- Moving from another router is not documented here. The differences that matter would be differences from that
  product's behaviour, and we do not document other people's products from the outside.
