Streaming works the same way it does on OpenAI’s API. Set `"stream": true` in the request body, read the server-sent events as they arrive, and stop when you see `data: [DONE]`. If your client already streams from an OpenAI-compatible endpoint, it will stream from Hopscotch with no changes.

## Turn on streaming with `stream: true`

```bash
curl https://api.hopscotchlabs.ai/v1/chat/completions \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -N \
  -d '{
    "model": "openai-main/gpt-4o-mini",
    "messages": [{"role": "user", "content": "Say hi in five words."}],
    "stream": true
  }'
```

The response has `Content-Type: text/event-stream`. The body is relayed as it
arrives: nothing is buffered on our side, so the first token reaches you as soon
as the model produces it.

### Streaming on the Responses API

`POST /v1/responses` streams too. It uses the same request path as chat completions, so everything on this page also applies to it: how the stream is relayed, where token counts appear, and how a stream can end early.

Only the event format is different. A Responses stream sends named events in the provider’s own shapes, forwarded as they arrive. It doesn’t send the chat completion chunks shown in the next section, so parse these events using the Responses format.

Both formats end the same way. Token counts arrive on the same `:x-hopscotch-usage` comment line, and the same error codes can cut a stream short.

## What the transcript looks like

Annotated. Ids and content are illustrative; the framing is exact.

```text
data: {"id":"chatcmpl-EXAMPLE","object":"chat.completion.chunk","model":"openai-main/gpt-4o-mini","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

data: {"id":"chatcmpl-EXAMPLE","object":"chat.completion.chunk","model":"openai-main/gpt-4o-mini","choices":[{"index":0,"delta":{"content":"Hello"},"finish_reason":null}]}

data: {"id":"chatcmpl-EXAMPLE","object":"chat.completion.chunk","model":"openai-main/gpt-4o-mini","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

:x-hopscotch-usage {"v":1,"reported":true,"prompt_tokens":12,"completion_tokens":8,"total_tokens":20}

data: [DONE]
```

<Warning>
  **The usage comment line was `:x-uniblock-usage` until 2026-09-18 and is now
  `:x-hopscotch-usage`.** The line's position, its JSON value and every field in
  it are unchanged; only the name after the colon moved, completing the
  retirement the response headers went through on 2026-09-14. There is no
  transition period on this one: a stream carries the new name alone. If you
  match the line by prefix, match `:x-hopscotch-usage`.
</Warning>

Everything except the `:x-hopscotch-usage` line is the standard format. That line
is a comment: the server-sent events specification requires a parser to ignore
any line beginning with a colon, so SDKs and browsers skip it and your streaming
loop never sees it. It sits immediately before `data: [DONE]` and never after,
because the counts are final only at that point and a client that stops reading
at the terminator would otherwise miss it.

<UsageHeader />

Absent counts are omitted rather than sent as zero, and `"reported": false`
carries no counts at all. The full field list is in
[Headers](/api-reference/headers#token-counts).

## Get usage in a stream chunk with `include_usage`

The comment line above is ours. If you want token counts as part of the stream
your SDK parses, ask for them the standard way:

```json
{
  "model": "openai-main/gpt-4o-mini",
  "messages": [{"role": "user", "content": "Say hi in five words."}],
  "stream": true,
  "stream_options": {"include_usage": true}
}
```

You then get the usual final chunk with an empty `choices` array and a `usage`
object, ahead of `data: [DONE]`. If you do not ask for it, you do not receive it,
because the commonest streaming loop in every language reads
`chunk.choices[0].delta` and throws on a chunk that has no choices.

## When a stream ends early

By the time anything can go wrong in a stream, the status code and headers have already been sent. That means an error can’t come back as a status code. The stream sends one final `data:` line with the standard error body and then closes. No `data: [DONE]` follows it.

```
data: {"error":{"message":"Your credit ran out while this request was still running, so it was stopped rather than finished. You have been charged only for what was produced before that point. Add credit and send it again.","type":"insufficient_quota","param":null,"code":"balance_exhausted","request_id":"00000000-0000-4000-8000-000000000000"}}
```

Three codes can end a stream:

| `code` | What happened | What to do |
|---|---|---|
| `balance_exhausted` | Credit ran out while the request was running. | Buy credit and send it again. You are charged for what was produced before the cut and nothing more. |
| `balance_unavailable` | We could not check the balance while the request was running, so we stopped it rather than leave it unwatched. | Retry shortly. This is ours, and it does not mean you are out of credit. |
| `request_deadline_exceeded` | The request ran past the 540 second limit. | Split the work into smaller calls. |

You’ll only see `balance_exhausted` in the middle of a stream. If your account can’t pay before a request starts, you get a `402` with `insufficient_credit`. This way you can always tell a request that never started from one that was cut off partway. Neither one is charged as a full request. A refused request costs nothing, and a cut-off stream costs only the output it produced.

If a stream stops with neither `data: [DONE]` nor an error line, the connection dropped. Treat the response as incomplete because the answer is truncated. We log it as an unfinished stream, and it isn’t counted as a fault.

## What streaming does not change

- Billing works the same way. Credit is held before the request goes out, and a
  streamed request is metered and appears in your usage like any other.
- Errors use the same body and the same codes as a non-streamed request. Only the
  channel differs, and only because a status code cannot be recalled.
- The bytes are the provider's. We add the one comment line and relay everything
  else exactly as it arrived.
