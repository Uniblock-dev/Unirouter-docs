You name a model in the `model` field of a request, as you would with OpenAI. The name says which
provider serves it, so one key and one endpoint reach models from more than one place.

## Model ids

An id is a provider and a model name, split on the **first** slash:

```json
{ "model": "openai/gpt-4o-mini" }
```

The part after the slash is the provider's own id with the maker's namespace removed. A model a provider
publishes as `openai/gpt-oss-120b` is `groq/gpt-oss-120b` here. An id with no namespace is unchanged, as in
`anthropic/claude-opus-4-5`. Each name is fixed the first time we publish that model on that provider, so an
id in your code stays put.

You choose the provider, and we never substitute another. A model carried by two providers is two ids with
two prices.

The `model` field accepts three forms:

| Form | What it does |
|---|---|
| `provider/model` | That model from that provider. If it cannot serve the request, the request fails rather than moving to another host. The half after the slash may be the pinned name or a shorter name we hold, such as `anthropic/opus`, which is served and answered as the pinned id. A name we do not hold is refused with a `404` naming the provider and the id. |
| `profile/{identifier}` | A [routing profile](/features/routing-profiles) you built. |
| `unirouter/auto` | Whichever route you made your default, or a list we publish for your cost tier. `hopscotch/auto` is a second spelling. |

A bare id such as `gpt-4o-mini`, or a bare `opus`, is refused with `400` and the code `model_id_not_pinned`.
Ask for ids rather than building them by hand.

The single-model lookup, `GET /v1/models/{id}`, also accepts the provider's own spelling, so an old link or
usage record still opens. The request path does not, so an id that works in a lookup may not be callable.
This site publishes no list of models, families or providers, because a stale list is worse than none.

## Discovering what you can call

**Over the API.** `GET /v1/models` returns an OpenAI-shaped list. Each entry has an `id` (the value for
`model`), its input rate and, where separate, its output rate, a context window, capabilities, the currency and the provider names behind it. `GET /v1/models/{id}` adds a short description, the request parameters with
their bounds and defaults, and any deprecation and sunset dates with the named replacement. The description
comes from third-party model catalogues and appears only on the single-model call.

```bash
curl https://api.hopscotchlabs.ai/v1/models \
  -H "Authorization: Bearer ub_live_XXXXXXXXXXXX"
```

Percent-encode the id once or send it as it is. A double-encoded slash names no model and answers `404`.

**In the dashboard.** The Models screen and the [Playground](/features/playground) offer the same catalog.
The Models screen shows one row per model and folds its providers together, with price ranges. Opening a row
gives one line per provider with its callable id. The row itself is not callable: take the `model` value from a provider line.

A catalog row with no provider identity is left out rather than shown as a bare id. So is a model that names no endpoint it can be called on, such as chat or embeddings, even when it carries a price.

## A model is offered only when it is live

A model appears only when we hold a working credential of our own for it, it is enabled on our side, and it
carries a price we have decided. You are never offered a model that would fail on call, nor one whose cost we
cannot tell you. A model with only a placeholder price is left out and answers as unknown when named.

Your own key for a provider changes which credential answers your calls. It cannot add a provider or a model.
See [Bring your own key](/features/bring-your-own-key). A request for a model that is not live, or that your
workspace may not use, is refused with an error that names the reason. See [Errors](/api-reference/errors).

## What a request costs

A served request deducts the provider's rate at face value, with no markup. The platform fee is added when you
buy credit, not when you spend it. See [Credits and billing](/manage/credits-and-billing). So compare the
purchase fee, not the call price, with calling a provider directly.

## How a model's rate is expressed

A model has a price per kind of token. The kinds are `input`, `cache_read`, `cache_write`, `output` and
`reasoning`, and they partition each request:

```text
prompt     = input + cache_read + cache_write
completion = output + reasoning
```

`input` excludes cached tokens, unlike a provider's `prompt_tokens`, which usually includes them. Cache reads
are commonly discounted, and cache writes cost more on some providers and do not exist on others. A rate can
carry a tier, a condition under which a different price applies, such as batch or priority. The default tier
has no conditions.

A charge names the rate revision in force when it was made. Changing any rate mints a new revision, so a later
price change cannot rewrite a past charge. The catalog describes prices in this same vocabulary, but your usage record, not the catalog, is the
authority on what a request cost.
