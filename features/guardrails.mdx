A guardrail is a named set of rules you attach to one or more API keys. Use it to cap spend, require zero data retention, limit which providers, models and regions a key can use, set token ceilings, and block prompts that match a pattern or contain sensitive data.

Every request on a governed key is checked against its guardrail before anything is sent to a provider.

Guardrails belong to your workspace. You manage them on the **Guardrails** screen in the dashboard, between **Keys** and **BYOK**.

## Where the policy belongs

Three settings can refuse or shape a request, at three levels.

| Layer | Where it is set | What it governs |
|---|---|---|
| Workspace | Workspace settings | Limits and the zero-data-retention default for every key. See [Spend controls](/manage/spend-controls) and [Zero data retention](/manage/zero-data-retention). |
| Guardrail | Guardrails screen | A named rule set attached to one or more keys. While attached, it replaces that key's own credit limit and zero-data-retention value. |
| Key | Keys screen | A key's own expiry and credit limit, used only when no guardrail governs the key. |

A key is governed by at most one guardrail at a time, and one guardrail can govern as many keys as
you like. Attaching a second guardrail to a key is refused rather than stacked. A guardrail does not
change the workspace setting for keys it does not govern.

## The guardrail's values take over completely

While a guardrail governs a key, only the guardrail's spend cap and zero-data-retention setting count. The key's own values stay saved but do nothing until you detach the guardrail.

The two sets of values aren't combined. If the guardrail has no spend cap, the key has no spend cap either, even if you set a credit limit on the key itself.

To keep this clear, the **Keys** screen won't let you edit a governed key's limits. It shows:

> This key is governed by guardrail NAME, so its own limits cannot be changed.

## The rules

A guardrail can hold nine rules. If you try to save a rule name Hopscotch doesn't recognize, the save fails and the error lists the nine valid names.

| Rule | What it does | Set it in the dashboard? |
| :-- | :-- | :-- |
| Spend cap | Caps spend at a dollar amount per day, week or month | Yes |
| Zero data retention | Sends requests only to zero-retention providers. On, off, or follow the workspace. | Yes (**Privacy**) |
| No training | Sends requests only to providers that don't train on inputs | Coming soon |
| Provider allow list | Limits which providers can serve the key | Coming soon |
| Model allow list | Limits which models the key can call | Coming soon |
| Region | Limits which regions can serve the key | Coming soon |
| Token limit | Sets input and output token ceilings | Coming soon |
| Injection patterns | Blocks prompts that match a regular expression | Coming soon |
| Sensitive data | Blocks requests that contain emails, IP addresses or passwords | Yes |

Today the dashboard can set the guardrail's name, spend cap, zero-data-retention choice and sensitive-data detectors. The other rules appear under **Coming soon** on the form. Once a rule is on a guardrail, it's enforced on every request, whether or not the dashboard can edit it yet.

### How each rule works

#### Spend cap

- **Amount:** a dollar figure with up to two decimal places. Zero isn't allowed.
- **Period:** `daily`, `weekly` or `monthly`. The period is required. A cap without one fails to save, so you can't end up with an accidental "unlimited" cap.
- **What counts:** only credit spent from your Hopscotch balance. Requests served on your own provider key never count toward the cap. See [Bring your own key](/features/bring-your-own-key).

#### Zero data retention and no training

- **Zero data retention on:** the request only goes to providers whose published terms say zero retention _and_ no training.
- **No training on:** the request only goes to providers that don't train on inputs. Retention isn't checked.
- If no eligible provider serves the model in the request, the request is refused and isn't sent anywhere.

In the dashboard, the **Privacy** setting can be **On**, **Off** or **Workspace default**. See [Zero data retention](/manage/zero-data-retention).

#### Provider, model and region allow lists

- Each list holds up to 100 entries, each up to 200 characters.
- A region list can only use these five words: `us`, `eu`, `uk`, `apac`, `global`.
- A request that falls outside a list is refused before it's sent.

#### Token limits

Pick a tier, or set your own ceilings.

| Tier | Input tokens | Output tokens |
| :-- | :-- | :-- |
| `low` | 8,000 | 1,000 |
| `medium` | 32,000 | 4,000 |
| `high` | 128,000 | 16,000 |

A custom ceiling is a whole number of tokens, up to `2,000,000`.

The two ceilings behave differently:

- **Input ceiling:** if the estimated prompt is over the ceiling, the request is refused.
- **Output ceiling:** never causes a refusal. Hopscotch lowers the `max_tokens` it forwards to the ceiling, or to the model's own maximum if that's lower. Requests still go through; replies are just capped in length.

## What a refused request sees

Every guardrail refusal is an error in the OpenAI envelope, with a code you can branch on. Nothing is charged
or held for a request a guardrail stops, and the message always names the guardrail.

| Rule | Status | `type` | `code` |
|---|---|---|---|
| Spend cap | 402 | `insufficient_quota` | `key_limit_exceeded` |
| Zero data retention, no training | 403 | `permission_error` | `no_zdr_eligible_provider` |
| Provider or model allow list | 403 | `permission_error` | `guardrail_not_permitted` |
| Region | 403 | `permission_error` | `no_region_eligible_provider` |
| Token limit, input | 400 | `invalid_request_error` | `guardrail_token_limit_exceeded` |
| Injection pattern | 403 | `permission_error` | `injection_pattern_matched` |
| Sensitive data | 403 | `permission_error` | `sensitive_data_matched` |

The spend cap reuses the code a key's own credit limit uses, because to the caller it is the same event. The
message names the guardrail to tell them apart: "This cap is set by guardrail \"prod-agents\", not on the key
itself."

Rules are checked in a fixed order: which providers may serve the key, then injection patterns, then
sensitive-data detectors, then the token ceiling and the spend cap. A request that breaks two rules is refused
for the first in that order.

If a token limit, an injection rule or a sensitive-data rule cannot be read when a request arrives, the request
is refused with HTTP 503 and a code ending in `_unreadable`, not served as if the rule were absent. Nothing is
sent. Re-saving the guardrail republishes it.

## Who can manage guardrails

Every member can see the guardrails and the keys each governs. Creating, editing, deleting,
attaching and detaching take owner or admin. See [Workspaces and members](/manage/workspaces-and-members).
The management API has the same operations, not yet published because its admin key is not available to customers. See [Management API](/manage/management-api).

## How to

### 1. Set up a guardrail

You need to be the owner or an admin, and the key you want to govern must already exist. See
[Authentication](/get-started/authentication).

<Steps>
  <Step title="Open Guardrails">
    Open **Guardrails** in the sidebar. With none yet, the screen reads "Nothing's fenced in yet" and points
    you at the create control, top right.
  </Step>
  <Step title="Name it">
    Names are unique within a workspace, ignoring case, and at most 120 characters. Make it say what the guardrail is for.
  </Step>
  <Step title="Set a spend cap, or leave it off">
    Turn **Spend cap** on, enter an **Amount** in dollars such as 100.00, and choose a **Period**: Daily, Weekly
    or Monthly. The amount is a whole number of cents above zero. With the cap off, the guardrail caps nothing.
  </Step>
  <Step title="Choose the zero-data-retention setting">
    Under **Privacy**, pick **Workspace default**, **On** or **Off**. On routes governed keys only to
    providers recorded as zero-data-retention. Off replaces the workspace setting with off for these keys.
  </Step>
  <Step title="Turn on sensitive-data detectors">
    Under **Sensitive-data detection**, switch on **Email addresses**, **IP addresses**, or **Passwords, secrets
    and API keys**. The last matches a name such as `password` written beside its value; a bare key is not matched.
  </Step>
  <Step title="Create">
    Press **Create guardrail**. The card appears with nothing attached yet.
  </Step>
</Steps>

The form lists Provider selection, Model selection, No training, Regions, Token limits and Injection checks
under "Coming soon". Those rules are enforced when a guardrail carries them, and the screen cannot write them yet.

### 2. Attach it to a key

You can attach from either screen. Both do the same thing.

- **From the guardrail:** on the guardrail's card, open **Keys this guardrail governs** and tick the keys. If a change doesn't save, you'll see: "The save did not finish, so the ticks above show where it stands." The ticks show what's actually saved.
- **From the key:** on the **Keys** screen, open the key's **Guardrail** cell, select **Attach to...**, and choose the guardrail. Only owners and admins see this cell.

After you attach a guardrail, the key's **Edit limits** control won't change its credit limit until you detach the guardrail. It tells you which guardrail is in the way.

If the key already has a guardrail, you'll see:

> This key is already governed by guardrail NAME. Detach it from that one before attaching it here.

### 3. Edit or delete a guardrail

**Edit** opens the same form you used to create it. Saving overwrites the whole guardrail, name included. Every attached key picks up the change before the save shows as done.

**Delete** asks you to confirm. You can't delete a guardrail that still governs keys. The error lists them:

> This guardrail still governs 2 keys: prod-api, prod-worker. Detach them before deleting it.

### 4. Find the block in Activity

Refused requests show up as normal rows in **Activity**.

1. Open **Activity**.
2. Filter by key, model or date.
3. Set the outcome filter to **refused**. The charge on these rows is zero.
4. Open a row to see the exact error code and the guardrail name.

The error the caller received has the same request ID, so you can match the two. See [View activity](/manage/usage-and-metering#look-up-one-request).

### 5. Fix a policy after a false positive

A false positive is a request the guardrail blocked that it should have let through.

1. **Find the rule.** The error code tells you which rule fired. You'll find it in Activity or in the caller's error.
2. **Make the smallest change that fixes it:**
   - **Spend cap:** raise the amount, change the period, or turn the cap off.
   - **Zero data retention:** set **Privacy** to **Workspace default** or **Off**.
   - **Sensitive data:** turn off the detector that matched.
   - **Injection patterns and allow lists:** you can't edit these in the dashboard yet. Detach the key to lift all of the guardrail's rules from it, so it runs on its own limits. Re-attach it once the rule has been changed in a supported place.
3. **Retry and check.** Send the same request again and watch Activity. If it's still refused, the new error code tells you which rule is still blocking it.
