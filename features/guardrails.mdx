A guardrail is a named set of rules that belongs to your workspace and applies to whichever API
keys you attach it to. Every request on those keys is judged against it before anything is sent to
a provider. Guardrails live on the **Guardrails** screen in the dashboard, between Keys and BYOK.

## Where the policy belongs

Three settings can refuse or shape a request, at three levels.

| Layer | Where it is set | What it governs |
|---|---|---|
| Workspace | Workspace settings | Limits and the zero-data-retention default for every key. See [Spend controls](/manage/spend-controls) and [Zero data retention](/manage/zero-data-retention). |
| Guardrail | Guardrails screen | A named rule set attached to one or more keys. While attached, it replaces that key's own credit limit and zero-data-retention value. |
| Key | Keys screen | A key's own expiry and credit limit, used only when no guardrail governs the key. |

A key is governed by at most one guardrail at a time, and one guardrail can govern as many keys as
you like. Attaching a second guardrail to a key is refused rather than stacked. A guardrail does not
change the workspace setting for keys it does not govern.

## A guardrail replaces the key's own limits

While a guardrail governs a key, its spend cap and zero-data-retention value are the ones in force, and
the key's own figures are kept but inert. This is replacement, not a floor or a ceiling: a guardrail with
no spend cap governs a key with no spend cap. The Keys screen refuses to change a governed key's limits:

> This key is governed by guardrail NAME, so its own limits cannot be changed.
> Detach it from the guardrail first.

## The rules

A guardrail carries a name and any combination of these rules. Every rule is optional, and a guardrail
with no rules is legal: it governs its keys and caps nothing.

| Rule | What it does |
|---|---|
| Spend cap | A dollar amount per day, week or month that requests on the key may spend from your balance. |
| Zero data retention | On, off, or inherit the workspace setting. On means only providers recorded as zero-data-retention may serve the key. |
| No training | Only providers recorded as not training on inputs may serve the key. |
| Provider allow list | The key may only call these providers. |
| Model allow list | The key may only call these models. |
| Region | The key may only be served from providers recorded in these regions: `us`, `eu`, `uk`, `apac` or `global`. |
| Token limit | An input ceiling and an output ceiling per request, as a preset tier or an explicit figure. |
| Injection patterns | Regular expressions that, if the prompt matches, stop the request. |
| Sensitive data | Detectors for an email address, an IP address, or a name such as `password` or `api_key` written beside its value. A match stops the request. |

The vocabulary is closed. A rule name the product does not know is refused when you save, and the refusal
lists the nine it does know.

**What the screen can write today.** The Guardrails screen edits the name, the spend cap, the
zero-data-retention choice and the sensitive-data detectors. The other rules sit under "Coming soon" on
the form and cannot be set from the dashboard yet. Every rule is enforced at request time once it is on a
guardrail.

### How each rule works

**Spend cap.** A dollar figure with at most two decimal places, and a period of `daily`, `weekly` or
`monthly`. A cap with no period is refused rather than read as unlimited. The cap counts credit spent from
your balance, so a request served on your own provider key never counts against it. See
[Bring your own key](/features/bring-your-own-key).

**Zero data retention and no training.** ZDR on requires a provider whose published retention is zero and
whose training is disabled; no training requires only the second half. A model the key names that no
eligible provider serves is refused, and the request is not sent anywhere.

**Allow lists and regions.** A provider list, a model list and a region list each hold up to 100 entries,
each up to 200 characters. A region list holds at most the five region words above. A request outside a
list is refused before it is sent.

**Token limits.** The tiers are `low` (`8,000` tokens in, `1,000` out), `medium` (`32,000` in, `4,000` out)
and `high` (`128,000` in, `16,000` out). An explicit ceiling is a whole number of tokens up to `2,000,000`.
The input ceiling refuses a request whose estimated prompt is above it. The output ceiling never refuses:
the `max_tokens` we forward is lowered to it, or to the model's own maximum if smaller, so a key under an
output ceiling gets shorter replies rather than refusals.

**Injection patterns and sensitive data.** An injection rule is up to 32 regular expressions, each up to
512 characters, run in a linear-time engine. A pattern that matches the empty string is refused at save time.
A sensitive-data rule names up to three detectors from the closed set `email`, `ip_address` and
`password_pair`. Both rules stop the request before any provider sees it. The refusal names the guardrail and
the detector, and never echoes the matched text or the pattern.

## What a refused request sees

Every guardrail refusal is an error in the OpenAI envelope, with a code you can branch on. Nothing is charged
or held for a request a guardrail stops, and the message always names the guardrail.

| Rule | Status | `type` | `code` |
|---|---|---|---|
| Spend cap | 402 | `insufficient_quota` | `key_limit_exceeded` |
| Zero data retention, no training | 403 | `permission_error` | `no_zdr_eligible_provider` |
| Provider or model allow list | 403 | `permission_error` | `guardrail_not_permitted` |
| Region | 403 | `permission_error` | `no_region_eligible_provider` |
| Token limit, input | 400 | `invalid_request_error` | `guardrail_token_limit_exceeded` |
| Injection pattern | 403 | `permission_error` | `injection_pattern_matched` |
| Sensitive data | 403 | `permission_error` | `sensitive_data_matched` |

The spend cap reuses the code a key's own credit limit uses, because to the caller it is the same event. The
message names the guardrail to tell them apart: "This cap is set by guardrail \"prod-agents\", not on the key
itself."

Rules are checked in a fixed order: which providers may serve the key, then injection patterns, then
sensitive-data detectors, then the token ceiling and the spend cap. A request that breaks two rules is refused
for the first in that order.

If a token limit, an injection rule or a sensitive-data rule cannot be read when a request arrives, the request
is refused with HTTP 503 and a code ending in `_unreadable`, not served as if the rule were absent. Nothing is
sent. Re-saving the guardrail republishes it.

## Who can manage guardrails

Every member can see the guardrails and the keys each governs. Creating, editing, deleting,
attaching and detaching take owner or admin. See [Workspaces and members](/manage/workspaces-and-members).
The management API has the same operations, not yet published because its admin key is not available to customers. See [Management API](/manage/management-api).

## How to

### 1. Set up a guardrail

You need to be the owner or an admin, and the key you want to govern must already exist. See
[Authentication](/get-started/authentication).

<Steps>
  <Step title="Open Guardrails">
    Open **Guardrails** in the sidebar. With none yet, the screen reads "Nothing's fenced in yet" and points
    you at the create control, top right.
  </Step>
  <Step title="Name it">
    Names are unique within a workspace, ignoring case, and at most 120 characters. Make it say what the guardrail is for.
  </Step>
  <Step title="Set a spend cap, or leave it off">
    Turn **Spend cap** on, enter an **Amount** in dollars such as 100.00, and choose a **Period**: Daily, Weekly
    or Monthly. The amount is a whole number of cents above zero. With the cap off, the guardrail caps nothing.
  </Step>
  <Step title="Choose the zero-data-retention setting">
    Under **Privacy**, pick **Workspace default**, **On** or **Off**. On routes governed keys only to
    providers recorded as zero-data-retention. Off replaces the workspace setting with off for these keys.
  </Step>
  <Step title="Turn on sensitive-data detectors">
    Under **Sensitive-data detection**, switch on **Email addresses**, **IP addresses**, or **Passwords, secrets
    and API keys**. The last matches a name such as `password` written beside its value; a bare key is not matched.
  </Step>
  <Step title="Create">
    Press **Create guardrail**. The card appears with nothing attached yet.
  </Step>
</Steps>

The form lists Provider selection, Model selection, No training, Regions, Token limits and Injection checks
under "Coming soon". Those rules are enforced when a guardrail carries them, and the screen cannot write them yet.

### 2. Attach it to a key

Attach from either side; both do the same thing.

- **From the guardrail.** On the card, open **Keys this guardrail governs** and tick the keys. A tick that will not save reads: "The save did not finish, so the ticks above show where it stands."
- **From the key.** On the **Keys** screen, open the key's Guardrail cell, then **Attach to...** and choose the
  guardrail. Only owners and admins are offered the cell.

Once attached, the key's **Edit limits** control refuses to change its credit limit, naming the guardrail, until
you detach it. A second attachment is refused: `This key is already governed by guardrail NAME. Detach it from
that one before attaching it here.`

### 3. Edit or delete a guardrail

**Edit** opens the same form. Saving replaces the whole guardrail, name included, and every attached key picks
up the change before the save is reported done.

**Delete** is behind a confirm, and a guardrail that still governs keys cannot be deleted. The refusal names them:
`This guardrail still governs 2 keys: prod-api, prod-worker. Detach them before deleting it.` The screen also
refuses a save with no name, a name already used in the workspace (`This workspace already holds a guardrail named "NAME". Names are unique per workspace, ignoring case.`),
and a spend cap of zero or with more than two decimals.

### 4. Find the block in Activity

Refused requests are ordinary rows in **Activity**. Open it, filter by key, model or date, and set
the outcome filter to **refused**. The charge reads zero. Open a row to see the exact code and the guardrail name.
The caller's error carries the same request id. See [View activity](/manage/usage-and-metering#look-up-one-request).

### 5. Fix a policy after a false positive

A false positive is a request the guardrail refused that should have been served. First find the rule: its code names it in Activity or in the caller's error. Then make the smallest change:

- **Spend cap.** Raise the amount or change the period, or turn the cap off.
- **Zero data retention.** Set the privacy choice to workspace default or off.
- **Sensitive-data detectors.** Switch off the detector that matched.
- **Injection patterns and allow lists.** These cannot be edited on the screen yet. Detach the key to lift all of its
  rules; it then runs on its own limits. Re-attach once the rule is changed in a supported place.

Send the same request again and watch Activity. If it is still refused, the code names the rule still in the way.
