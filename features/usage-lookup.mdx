Every response comes with a request id. Send that id to `GET /v1/usage/{id}` and you get back the usage record the dashboard shows for that request:

- token counts
- what it cost
- whether it was served
- how long it took

The endpoint reads the same record as the Activity screen, so the numbers always match. All it needs is the API key, which means a script or job can track its own spend without anyone signing in.

## How to

### Read one request back

Take the id from the `x-hopscotch-request-id` header of the response you want
to look up, or from `x-request-id`, which carries the same value for the
OpenAI SDKs, and ask for it:

```bash
curl https://api.hopscotchlabs.ai/v1/usage/REQUEST_ID \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE"
```

```json 200
{
  "object": "usage.request",
  "request_id": "REQUEST_ID",
  "occurred_at": "2026-10-20T14:03:11.412Z",
  "model": "openai-main/gpt-4o-mini",
  "outcome": "served",
  "streamed": false,
  "usage": {
    "prompt_tokens": 14,
    "completion_tokens": 9,
    "total_tokens": 23,
    "cache_read_tokens": null,
    "cache_write_tokens": null,
    "cache_write_1h_tokens": null,
    "reasoning_tokens": 0
  },
  "charge": {
    "amount_micros": 7500,
    "amount": "$0.0075",
    "currency": "USD",
    "rate_revision_id": "rr_01HXYZ",
    "note": "exact_from_provider_frame"
  },
  "served_on_own_key": false,
  "paid_from_allowance": false,
  "latency_ms": 812,
  "note": "No prompt and no response body was stored for this request; the figures here are everything that exists (we never store prompts)."
}
```

## The fields

| Field | What it holds |
|---|---|
| `request_id` | The id you asked for. |
| `occurred_at` | When the request began, as an `RFC 3339` timestamp. |
| `model` | The full `provider/model` id that was asked for. |
| `outcome` | Whether it was served, refused, or failed, in the vocabulary on [Usage and metering](/manage/usage-and-metering#the-outcome-vocabulary). |
| `streamed` | Whether the request asked for a stream. |
| `usage` | Seven token counts. A `null` means the provider did not report that count; a `0` means it reported none. The two are kept apart on purpose. |
| `charge` | What the request took from your balance: the amount in micro-dollars and as a decimal string, the currency, the rate revision it was priced under, and a note on how the figure was arrived at. Absent when the balance did not pay for the request. |
| `served_on_own_key` | Whether a provider key you brought served it, in which case we charged nothing. |
| `paid_from_allowance` | Whether a subscription seat's allowance paid for it rather than the balance. |
| `latency_ms` | How long the request took, end to end, as we measured it. |
| `note` | A sentence about what exists for this record. Today it says what the example above says: the bodies were never stored. |

Internal details are left out of the record. It doesn’t include our cost, the latency we added, or how many attempts the request took.

## When a record is not found

Every miss returns the same 404. You get it when the request:

- was made with a different key
- belongs to another workspace
- never existed

All three cases look identical, so nobody can use this endpoint to find out whether someone else’s request exists.

```json 404
{
  "error": {
    "message": "No usage record for \"REQUEST_ID\" is visible to this key. A record is written after the response is sent, so a read taken immediately can arrive first; a record made by another key, a record outside this key's workspace and an id that never existed answer identically.",
    "type": "not_found_error",
    "param": "request_id",
    "code": "request_not_found",
    "request_id": "REQUEST_ID"
  }
}
```

Pay attention to the first sentence of the message: no record for that id is visible to this key. The usual reason is timing. We write the usage record after we send you the response, so a lookup you send the moment the response arrives can get there before the record does. If you get a 404, wait a moment and retry once before you treat the request as missing.

Records are deleted after the retention window described on [Data and privacy](/manage/data-and-privacy). A lookup for an older request also returns a 404, but its charge stays on your statement.

## Read your balance and spend

The same API key also reads what its workspace has left and what it has
spent, with no dashboard session:

| Route | What it answers |
|---|---|
| `GET /v1/balance` | The workspace balance: available, settled, and the credit held for requests still in flight. |
| `GET /v1/usage` | Charged spend, tokens and requests by UTC day and model, the last 30 days unless `from` and `to` name another range. |
| `GET /v1/key/usage` | This key's own spend today, this week and this month, and its credit limit with what is left of it. |

```bash
curl https://api.hopscotchlabs.ai/v1/balance \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE"
```

```json 200
{
  "object": "balance",
  "currency": "USD",
  "available_balance": "18.50",
  "settled_balance": "20.00",
  "outstanding_reservations": "1.50",
  "as_of": "2026-10-21T15:30:00.000Z"
}
```

Amounts are exact decimal strings, so parse them as decimals. These reads
share a limit of their own, 60 a minute per key, apart from the request rate
your inference calls spend, so polling a balance never slows real traffic. The
[API reference](/api-reference/introduction) has every field and refusal.

### Key and credit reads as numbers

Two more reads return figures in another shape: under a `data` object, with
each amount as a JSON number rather than a decimal string. They suit a tool
that already expects to read a key's usage and limit, or its credits and
usage, in that shape.

| Route | What it answers |
|---|---|
| `GET /v1/key` | The figures `GET /v1/key/usage` returns: this key's spend as `usage_daily`, `usage_weekly` and `usage_monthly` (`usage` repeats the month), with `limit`, `limit_remaining` and `limit_reset`. |
| `GET /v1/credits` | `total_usage`, everything the workspace has been charged since its lifetime total began counting, and `total_credits`, which is that plus the settled balance. |

```bash
curl https://api.hopscotchlabs.ai/v1/credits \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE"
```

```json 200
{
  "as_of": "2026-10-21T15:30:00.000Z",
  "data": {
    "total_credits": 27.3,
    "total_usage": 7.3
  }
}
```

`total_usage` trails live spend by up to a few hours, so read `GET /v1/balance`
for a live figure. Each number is written from the exact decimal, but a client
that parses it into a double keeps about fifteen significant digits; read the
string routes above where every digit matters. Both count toward the same 60
reads a minute.
