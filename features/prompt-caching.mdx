Several providers cache part of a prompt, so resending it avoids paying full price for that part.
The feature is the provider's. It is asked for in the request body, which travels here unchanged, so it
works through this API as it does when you call the provider directly.

## How you ask for it

The same way you would upstream. A provider whose caching is explicit takes a marker in the body, which is
forwarded as you wrote it. A provider whose caching is automatic applies it without being asked, and nothing
here turns it off.

There is no Hopscotch control for caching, in the body or in a header, and nothing to enable in the dashboard.
Which providers cache, and on what terms, is the provider's own behaviour. This site publishes no per-provider
table, because a stale table about pricing is worse than none.

## Where the counts arrive

Cached tokens are reported separately from ordinary input tokens, in three places.

**In the reply body**, on a response that is not streamed, inside the provider's own `usage` object, in whatever
spelling that provider uses.

**On the stream**, as fields on the `:x-hopscotch-usage` comment line written immediately before `data: [DONE]`:

```text
:x-hopscotch-usage {"v":1,"reported":true,"prompt_tokens":1200,"completion_tokens":80,"total_tokens":1280,"cache_read_input_tokens":1024,"cache_write_input_tokens":0}
```

| Field | What it counts |
|---|---|
| `cache_read_input_tokens` | Input tokens served from the provider's cache. |
| `cache_write_input_tokens` | Input tokens written into it. |
| `cache_write_1h_input_tokens` | The part of those writes made with a one-hour lifetime. Already counted inside `cache_write_input_tokens`, and present only when the provider splits its writes by lifetime, as Anthropic does. |

**On your usage record**, and so on the Activity screen, as the cache read and cache write figures for that
request. See [Usage and metering](/manage/usage-and-metering).

### Absent is not zero

A field is omitted rather than sent as `0` when the provider did not report it. A provider that does no cache
accounting produces a usage line with neither field, which is a different fact from a request that used no
cache. So a missing `cache_read_input_tokens` means "we were not told", and `0` means the provider said none.
Every count is the provider's own. Nothing is re-counted or estimated.

## How cached tokens are priced

A model has a price per kind of token, and cache reads and cache writes are two of the five kinds:

```text
prompt = input + cache_read + cache_write
```

`input` excludes cached tokens, which is worth reading twice if you are used to a provider's `prompt_tokens`
including them. Reads are commonly discounted. Writes are priced above plain input by some providers and do not
exist on others. See [Models](/features/models) for the whole rate vocabulary.

The rate that applied is the one in force when the request was made, and a later price change cannot rewrite
it. Your usage record is the authority on what a request cost. A price in the catalog describes what a model
charges now.

## The cache status header is not this

A served response can carry `x-hopscotch-cache-status`. It describes how our side produced the answer, not
provider prompt caching. To learn whether your prompt cache was hit, read the token counts above. Read the
header in logs and build no behaviour on it. See [Headers](/api-reference/headers).

## Getting a cache hit at all

The rules are the provider's, but the general shape holds across providers that cache:

- **Put the stable part of your prompt first.** Caching works on a prefix, so an unchanging system prompt and
  document belong before the part that changes.
- **Do not reorder it between turns.** A prefix that differs by a timestamp, a reordered tool list or a
  regenerated id is a different prefix.
- **Short prompts are usually not cached.** Providers set a minimum, and below it nothing is cached.
- **Caches expire.** A cache read on one turn does not promise one on the next.

The way to know whether it worked is the counts. Read `cache_read_input_tokens` on a second identical request.

## What this platform does not do

**We do not cache your prompts.** No prompt or reply is stored here, which is a data fact first. See
[Data and privacy](/manage/data-and-privacy).

**We do not create a provider cache for you.** Nothing is inserted into your body. If the request carries no
cache marker and the provider's caching is explicit, nothing is cached.

**We make no promise about hit rates**, and no figure for one has been measured here in a way we will publish.
