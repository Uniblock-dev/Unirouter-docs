Several providers can cache part of your prompt, so you pay less for that part when you send it again. Caching is a provider feature that you request in the request body. We forward the body unchanged, so caching works through Hopscotch the same way it does when you call the provider directly.

## Request caching the way your provider expects

Request it the same way you would with the provider directly. If the provider uses explicit caching, add its cache marker to the request body and we forward it as written. If the provider caches automatically, it does so without being asked, and we don’t turn that off.

Hopscotch has no caching setting of its own. There’s nothing in the body, nothing in a header, and nothing to turn on in the dashboard. Each provider decides whether it caches and on what terms. We don’t publish a per-provider table, because pricing changes and an outdated pricing table does more harm than having none.

## Where to find cached-token counts

Cached tokens are reported separately from ordinary input tokens, in three places.

1. **In the reply body**, on a response that is not streamed, inside the provider's own `usage` object, in whatever spelling that provider uses.
2. **On the stream**, as fields on the `:x-hopscotch-usage` comment line written immediately before `data: [DONE]`:

```text
:x-hopscotch-usage {"v":1,"reported":true,"prompt_tokens":1200,"completion_tokens":80,"total_tokens":1280,"cache_read_input_tokens":1024,"cache_write_input_tokens":0}
```

| Field | What it counts |
|---|---|
| `cache_read_input_tokens` | Input tokens served from the provider's cache. |
| `cache_write_input_tokens` | Input tokens written into it. |
| `cache_write_1h_input_tokens` | The part of those writes made with a one-hour lifetime. Already counted inside `cache_write_input_tokens`, and present only when the provider splits its writes by lifetime, as Anthropic does. |

3. **On your usage record**, and so on the Activity screen, as the cache read and cache write figures for that request. See [Usage and metering](/manage/usage-and-metering).

### A missing count doesn’t mean zero

If the provider didn’t report a count, we leave the field out instead of sending `0`. A provider that doesn’t track caching returns a usage line with neither field, and that’s different from a request that got no cache hits. A missing `cache_read_input_tokens` means the provider didn’t tell us. A `0` means the provider reported none. Every count comes from the provider, and we don’t recount or estimate anything.

## How cached tokens are priced

A model has a price per kind of token, and cache reads and cache writes are two of the five kinds:

```text
prompt = input + cache_read + cache_write
```

`input` excludes cached tokens, which is worth reading twice if you are used to a provider's `prompt_tokens`
including them. Reads are commonly discounted. Writes are priced above plain input by some providers and do not
exist on others. See [Models](/features/models) for the whole rate vocabulary.

The rate that applied is the one in force when the request was made, and a later price change cannot rewrite
it. Your usage record is the authority on what a request cost. A price in the catalog describes what a model
charges now.

## Don't use `x-hopscotch-cache-status` to check cache hits

A served response can carry `x-hopscotch-cache-status`. It describes how our side produced the answer, not
provider prompt caching. To learn whether your prompt cache was hit, read the token counts above. Read the
header in logs and build no behaviour on it. See [Headers](/api-reference/headers).

## How to get a cache hit

Each provider sets its own rules, but the basics are the same across providers that cache:

- **Put the stable part of your prompt first.** Caching works on the start of the prompt (the prefix), so put your unchanging system prompt and documents before the parts that change.
- **Keep that prefix identical between turns.** A changed timestamp, a reordered tool list, or a regenerated ID makes it a new prefix.
- **Short prompts usually aren’t cached.** Providers set a minimum length, and nothing shorter gets cached.
- **Caches expire.** A cache hit on one turn doesn’t guarantee one on the next.

To check whether caching worked, send the same request twice and look at `cache_read_input_tokens` on the second response.

## What this platform does not do

**We do not cache your prompts.** No prompt or reply is stored here, which is a data fact first. See
[Data and privacy](/manage/data-and-privacy).

**We do not create a provider cache for you.** Nothing is inserted into your body. If the request carries no
cache marker and the provider's caching is explicit, nothing is cached.

**We make no promise about hit rates**, and no figure for one has been measured here in a way we will publish.
