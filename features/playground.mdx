The playground is a chat screen in the dashboard that sends a real request to a real model. It is not a
simulator and not a sandbox.

<Warning>
A playground run spends real credit from this workspace's balance, at the same rate an API call to the same
model would. There is no free tier on this screen.
</Warning>

## Every run sends as one of your keys

Before you send, pick a key in the control labelled `Send as key`. Its tokens and charge land on that key's
line, which is what makes a playground run and an API call read the same in your usage.

The key is attribution, not authentication. Your dashboard session authenticates the playground, and the key
decides whose line the spend lands on. You never paste a key secret, because only a hash of it exists.

**No key means no playground.** A workspace with no keys cannot use the screen. It says so and points at Keys.
Sending without a key is refused: "Pick a key, or create one on the Keys screen if this workspace has none yet."

You can send as exactly the keys your key list shows. An owner or admin can send as any key in the workspace.
A reserved key that has not been viewed yet is not offered. A key that does not exist and a key you may not see
get the same refusal, "That is not a key you can send as in this workspace.", so the screen cannot reveal hidden
keys. See [Who can see which keys](/get-started/authentication#who-can-see-which-keys).

## What a run does to your balance

A run is admitted, held and settled the same way an API request is, through the same code path. The request
that leaves us is identical either way.

- It holds an estimated maximum before the model is called. A run you cannot pay for is refused before it
  reaches a provider.
- It settles at the provider's rate at face value, with no markup.
- It writes a usage record on the key's line, alongside the member at the keyboard. The key says whose line
  the spend lands on; the member says who sent it.

So a model tested in the playground and then called through the API tell one story about the same spend.

## Nothing is stored

The prompt and the reply are not stored, here or on our side. The screen says so: "The playground keeps no
history, because we never store prompts. Leaving this screen loses what is on it." There is no history, no
saved session and no shareable link. Keep a prompt on your side if you need it. See
[Data and privacy](/manage/data-and-privacy).

The metadata is kept like any request: model, token counts, cost, latency and outcome. That is why a run shows
in your usage without its content.

## The metrics line

Each reply carries one line of labelled figures: time to first token, total time, tokens per second, tokens in
and tokens out. A figure that was not measured reads `unknown`, not `0`.

- **Time to first token reads `unknown`.** The playground does not stream yet, so the reply arrives whole. A
  streamed API request does carry that timing.
- **No cost appears on this line.** Read a run's cost in your usage. See
  [Usage and metering](/manage/usage-and-metering).

## Refusals you may hit

- **Requests are paused.** If the owner has paused the workspace, playground runs are refused too. Every member
  can read the pause state; only the owner changes it. See [Spend controls](/manage/spend-controls).
- **The workspace is suspended.** "This account is suspended, so it cannot send requests. Contact support."
- **No credit.** A run the balance cannot cover is refused before the model is called. Nothing is charged for a
  refused request. See [Credits and billing](/manage/credits-and-billing).

## What is not built yet

- No streaming, so the reply arrives complete.
- No cost preview before sending, and no cost figure after.
- No generation settings beyond the model and the key.
- No warning before a run exceeds your balance, other than the refusal itself.

The whole conversation is sent again on every turn, which is how a stateless completions API remembers anything.
A long conversation costs more per turn, because the prompt grows.

## What we did not verify

The behaviour on this page comes from the shipped screen and the route behind it, including the key requirement
and the refusal wording. It was not exercised against a deployed environment for this documentation, and the
playground stories that would accept this screen are still open.
