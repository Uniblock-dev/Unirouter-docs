Models differ in what they will accept, not just in what they cost. Every entry
in the catalog carries a `capabilities` object saying what this one can do, so
you can decide before you spend a request finding out.

## The five cababilities

```json
{
  "capabilities": {
    "streaming": "yes",
    "tools": "yes",
    "json_mode": "yes",
    "vision": "yes",
    "audio": "no"
  }
}
```

It rides inside the `uniblock` block on every entry from `GET /v1/models` and on
`GET /v1/models/{id}`.

| Word | The question it answers |
|---|---|
| `streaming` | Will `"stream": true` produce server-sent events? See [Streaming](/features/streaming). |
| `tools` | Does it take a `tools` array and answer with `tool_calls`? See [Tool calling](/features/tool-calling). |
| `json_mode` | Does it take a `response_format`? See [Structured outputs](/features/structured-outputs). |
| `vision` | Does it take an image part in a message? See [Image inputs](/features/image-inputs). |
| `audio` | Does it take audio input? |

## Three answers, not two

Each word is `yes`, `no`, or `unknown`, and the third one is the point.

**`unknown` is not `no`.** It means nobody has established the answer for this
model yet, not that the answer is negative. A model whose capabilities are all
`unknown` is a model we have not learned anything about, not a model that can do
nothing.

We could guess instead, but a wrong `no` does the most damage. Anyone who filters on that field would never see the model, and nothing would tell them it was missing. So when we don’t know, the catalog says `unknown`.

What that means for your code:

- **Filtering on `=== "yes"`** gives you the models we can vouch for, and skips
  some that would have worked.
- **Filtering on `!== "no"`** gives you everything not ruled out, and includes
  some that will fail.
- **Branching on truthiness** is the bug this field exists to prevent. All three
  values are non-empty strings.

## Capabilities don’t block requests

We don’t check your request against these values. If you send an image to a model whose `vision` is `no`, we forward the request anyway. The provider rejects it with its own error message and status code, and we pass that error back to you as-is.

This is the same rule as everywhere else on the request path: your body reaches
the provider as you wrote it, and the provider answers for it. See
[Request parameters](/api-reference/parameters).

So check the catalog when you pick a model, before you send anything. Reading a capability value costs nothing. A failed request costs you a round trip, and it only tells you how one provider serves the model.

## Where capabilities come from

Each capability value is an answer we’ve recorded. We base it on what the model’s own sources publish and on what we see when we run the model. When those disagree, we go with the stronger evidence. If we have no evidence, the value stays `unknown` and never falls back to a default.

Keep two things in mind before you build on these values:

- **A value can change even if the model doesn’t.** New evidence about a model can update its values, so re-read the catalog now and then. Don’t cache it forever.
- **The value describes the model as it’s listed in this catalog.** It’s our best answer, but the provider hasn’t promised it. If we don’t have an answer, you’ll see `unknown` and never a confident guess.

## What is not here

**A capability matrix.** Which models support what changes often, sometimes without any release on our side. A table here would be out of date the first time that happened, so the current answer lives in the catalog. Call `GET /v1/models`.

**Capability details per provider.** When two providers serve the same model, it appears as two entries with different ids, and each entry has its own capability values. That’s the most detailed view the public API offers today.
