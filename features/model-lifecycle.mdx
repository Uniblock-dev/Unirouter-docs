Every model you can call today is run by a provider, and at some point the provider will turn it off. The catalog publishes the dates for that, so a failed request isn’t how you find out. This page explains what each date means and what to do about it.

## Two dates, two meanings

They are different facts and a model can carry either without the other.

| Date | What it says |
|---|---|
| Deprecated | Prefer something else. The model still answers. |
| Sunset | This stops answering. After it, the model is gone. |

Deprecation is a recommendation. The provider has stopped recommending the model, usually because there’s a newer one, but your requests keep working the same way. Sunset is the date the model stops answering requests.

## Where they are

**In** `GET /v1/models`, each model’s sunset date appears as `shutdown_date`, in unix seconds. It sits at the top level of the model object, where OpenAI’s own model format puts it. If a model has no sunset date, the key is missing entirely instead of being set to `null`. Check whether the key exists, not what its value is.

```json
{
  "id": "openai/gpt-4o-mini",
  "object": "model",
  "created": 1756080000,
  "owned_by": "openai",
  "shutdown_date": 1790000000,
  "uniblock": { }
}
```

It is on the list, and not only on the detail, precisely so that a client can
find every model it depends on that is ending without fetching each one.

In `GET /v1/models/{id}`, three fields inside the `uniblock` block give you the full picture:

```json
{
  "deprecated_at": 1780000000,
  "sunset_at": 1790000000,
  "replacement_model_id": "openai/gpt-4o-mini-2"
}
```

| Field | What it is |
|---|---|
| `deprecated_at` | Unix seconds, or null. When the model stopped being recommended. |
| `sunset_at` | Unix seconds, or null. When it stops answering. |
| `replacement_model_id` | The id to move to, or null. |

**Expect** `replacement_model_id `**to be** `null `**most of the time. That’s on purpose.** We only fill it in when the provider has named a successor. We never guess, because you’d act on a wrong guess and move to the wrong model.

## What happens when a model reaches its sunset

The model is removed from `GET /v1/models` and from the Models screen, and any request that names it is refused.

The refusal comes back as a `404`, and the error message tells you why. If the provider has **retired** the model, the message says it’s gone for good and that retrying won’t help. Use that message to decide what to do next, because backing off and retrying will never reach a model that’s been switched off. See [Errors](/api-reference/errors).

The dates come from the provider, so a model can stop before its published sunset if the provider stops serving it early. When that happens, the model drops out of the catalog right away, whatever the announced date says. The whole catalog works this way: it only lists models you can actually call.
See [Models](/features/models).

## Building for it

**Read the catalog rather than pinning a list.** A model id hard-coded in your
source is a deployment you will have to do at short notice one day. Ask
`GET /v1/models` and treat the answer as current rather than permanent.

**Check `shutdown_date` on the models you use, not on all of them.** One pass
over the list, filtered to the ids your application sends, tells you what is
ending and when.

**Treat a deprecation as a scheduling problem and a sunset as a deadline.** They
are usually months apart, and the gap is the whole point of publishing both.

**Move deliberately rather than automatically.** `replacement_model_id`, where it
is set, is what the provider says the successor is. It is not a promise that the
successor behaves like its predecessor on your prompts, prices the same, or has
the same capability words. Read
[Model capabilities](/features/model-capabilities) for the model you are moving
to, and test before you cut over.

**A model id names a provider.** A model that ends at one provider may still be
served by another, as a different id with its own price. See
[Models](/features/models) for how ids are shaped.

## What is not here

**A schedule of upcoming shutdowns.** It would be a list, on a page, going stale.
The dates are in the catalog, per model, and that is the copy that is current.

**Any notice we send you.** Nothing on this site promises an email or a dashboard
warning before a model ends, because no such notice exists in what has shipped.
Read the dates.
