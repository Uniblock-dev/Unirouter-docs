Tool calling on Hopscotch uses OpenAI’s format. You send a `tools` array in the request body and the model replies with `tool_calls`. Your code runs the tool and sends the result back as a `tool` message. Sending the request through Hopscotch doesn’t change any step of that loop.

## Tool requests and replies pass through unchanged

`tools`, `tool_choice` and `parallel_tool_calls` are regular body fields, and they reach the provider exactly as you wrote them. Hopscotch doesn’t put its own schema in front of yours. Tool definitions your client already builds work right away, so you don’t have to wait for us to add support.

The reply comes back the same way. On a response that is not streamed,
`choices[0].message.tool_calls` is the provider's own array, unchanged. On a
streamed response, `tool_calls` arrive in `choices[0].delta` and the stream ends
with `finish_reason` set to `tool_calls`, exactly as your existing streaming
parser expects.

<CodeGroup>

```bash curl
curl https://api.hopscotchlabs.ai/v1/chat/completions \
  -H "Authorization: Bearer ub_live_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai-main/gpt-4o-mini",
    "messages": [{"role": "user", "content": "What is the weather in Oslo?"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Current weather for a city.",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string"}},
          "required": ["city"]
        }
      }
    }]
  }'
```

```python Python
response = client.chat.completions.create(
    model="openai/gpt-4o-mini",
    messages=[{"role": "user", "content": "What is the weather in Oslo?"}],
    tools=[{
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Current weather for a city.",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        },
    }],
)

for call in response.choices[0].message.tool_calls or []:
    print(call.function.name, call.function.arguments)
```

</CodeGroup>

## Which models take tools

Ask the catalog. Every entry carries a `tools` word in its `capabilities` block,
answering `yes`, `no` or `unknown`. See
[Model capabilities](/features/model-capabilities), and read the part about
`unknown` before you filter on it.

The `tools` capability in the model catalog tells you whether a model supports tools, but Hopscotch doesn’t enforce it. If you send a `tools` array to a model that doesn’t support tools, we forward it anyway. You get back the provider’s own error, in the provider’s own words. We don’t block the request ahead of time, so the place to check `tools` is when you choose a model.

## What a tool-calling loop costs

A tool-calling loop is a series of requests, and each turn counts as a full request. It’s billed, it shows up as its own row in Activity, and it counts toward your key’s request rate limit and your account’s spend rate cap.

Two things tend to surprise people:

1. **Tool definitions count as prompt tokens on every turn.** Your `tools` array goes out with the request body on each pass through the loop, so you pay for a large one on every turn. The token counts in the response come straight from the provider and already include it.
2. **A turn that only calls a tool still uses output tokens.** The model generates the `tool_calls` array as text. If a loop takes several turns to reach an answer, you pay for the output of each one.

Set `max_tokens` on every turn. It decides how much credit we hold while a request runs, and a loop holds credit again on each turn. See [Rate limits and spend controls](/manage/spend-controls).

## Errors in the middle of a loop

Everything on [Errors](/api-reference/errors) applies unchanged, and one habit is
worth building. A loop that retries blindly on any failure can spend real credit
turning one broken tool definition into a long conversation with itself. Branch
on `type` and `code`: a `400` will fail identically on retry, and a `429` with
`rate_limit_exceeded` carries `Retry-After`.

Hold the request id from each turn. When a loop goes wrong, the useful question
is which turn, and the id is what answers it.

## What this platform does not do

**We do not run tools for you.** There are no hosted tools, no web search, no
code execution, no sandbox. Every tool in your `tools` array is executed by your
own code, and the only thing on our side is the request that carries it. If a
provider offers a tool that runs on the provider's own side, that is between your
body and that provider.

**We do not repair tool arguments.** A model that emits arguments which do not
match your schema emits them to you unchanged. Nothing here validates the
arguments against the schema you sent, and nothing retries to get a better
answer.

**We do not remember a conversation.** Every request carries its whole
`messages` array, tool results included. Nothing is stored on our side between
turns, which is the same fact as [Data and privacy](/manage/data-and-privacy)
seen from a different angle.
