Some models generate reasoning tokens before they answer. This is text the model writes to work through the problem. You usually don’t see it, but you always pay for it. Hopscotch doesn’t change any of that. Three things are still worth knowing, because reasoning is where a request most often costs more than you’d expect.

## Control reasoning with `reasoning_effort`

Use `reasoning_effort` where the model supports it. On Vertex Gemini we translate it into Google's thinking-level control; other providers may accept different values or their own native controls. See [Gemini on Vertex](/features/vertex-gemini) for a model-specific request.

The model decides which values it accepts. An unsupported value can be refused by the provider, or while we translate it for a specific provider. There's one value we always reject ourselves: an empty or whitespace-only `reasoning_effort` gets a `400`, `code` `invalid_value`, and `param` set to `reasoning_effort`. Gemini also rejects malformed levels and values the selected model doesn't support. See [Request parameters](/api-reference/parameters).

## Reading the completion and reasoning counts

For providers that include reasoning in completion usage:

```text
completion = output + reasoning
```

For those providers, reasoning tokens are part of `completion_tokens`, not a figure to add to it. When
a provider reports them, the count arrives separately as well, as a second view
of tokens already counted:

```text
:x-hopscotch-usage {"v":1,"reported":true,"prompt_tokens":40,"completion_tokens":900,"total_tokens":940,"reasoning_tokens":768}
```

In that line the model produced nine hundred completion tokens, of which the
great majority were reasoning and the rest were the answer you saw. Adding
`reasoning_tokens` to `completion_tokens` would count them twice.

Gemini is different: `completion_tokens` contains candidate output and reasoning
is reported separately. Do not subtract the reasoning count from Gemini's
completion count. Use the recorded charge for spend accounting instead of
applying one token formula across providers.

The same figure reaches your usage record and the Activity screen as the
reasoning count for that request. See
[Usage and metering](/manage/usage-and-metering).

**Absent is not zero.** `reasoning_tokens` is omitted rather than sent as `0`
when the provider did not report it, so a missing field means we were not told
rather than none were used. A model that does no reasoning at all produces a
usage line without the field.

## What reasoning costs

Reasoning is one of the five kinds of token a model's rate is expressed in, and
it earns a price of its own because providers price it separately.

See [Models](/features/models) for the whole vocabulary, and read what a request
actually cost from your usage record rather than from a rate.

## Set `max_tokens` high enough for reasoning and the answer

There are two reasons, and they push in opposite directions.

1. **Set it too low, and the model can use it all on reasoning.** Most providers count reasoning tokens against `max_tokens`. A limit that works fine for a regular model can run out before a reasoning model starts its answer. You get an empty or cut-off reply with `finish_reason` set to `length`, and you still pay for the reasoning. Check `finish_reason` before you parse anything.
2. **Leave it out, and we hold credit for the model’s full maximum.** While a request runs, we hold credit against its token limit. If you don’t send `max_tokens`, that limit is the model’s published maximum output, which is often large for reasoning models. The full hold comes back when the request settles, and you pay only for what the model produced. Until then, the hold takes up that much of your account’s spend rate cap. See [Rate limits and spend controls](/manage/spend-controls).

So always send `max_tokens`, and make it large enough for both the reasoning and the answer.

## Streaming a reasoning model

The stream comes straight from the provider. If the provider sends reasoning as its own type of delta, you get that delta unchanged. If it sends nothing until the thinking is done, you’ll see a long pause before the first chunk. We don’t fill that pause, and we don’t time out the request before its normal deadline.

The counts arrive at the end, on the usage comment line, as they do for any
stream. A stream cut off part way carries no usage line, because there are no
final counts to report. See [Streaming](/features/streaming).

## What this platform does not do

**We do not hide or strip reasoning content.** What the provider sends is what
you get. If a provider returns its reasoning in the body, it reaches you; if it
withholds it and reports only the count, that is the provider's choice and not
ours.

**We do not choose an effort level for you.** A request that names none is sent
naming none, and the provider's own default applies.

**We do not re-count anything.** Every figure above is the provider's own.
