A coding harness is an agent that edits your code, as an editor extension or a CLI. Most take a custom OpenAI-compatible base URL. This page covers what is true of all of them. Each per-harness page covers only its own settings and surprises.

Whether the value ends in `/v1` differs by harness. Getting it wrong produces a `404`, not a configuration error. Each harness page says which form it wants.

## Which wire your harness speaks

Settle this first. It decides whether the rest of this page applies.

| Wire | Harnesses | Notes |
|---|---|---|
| Chat completions | Cline, Continue, Aider, Zed, OpenCode, Cursor, Hermes Agent, Pi, DeepSeek Harness | Most of this site. |
| Responses API | Codex CLI | Codex has no other wire, since its project removed the chat setting. This API serves `POST /v1/responses`. |
| Anthropic Messages | Claude Code | [`POST /v1/messages`](/features/anthropic-messages). The base URL is an origin, with no `/v1`. |

Hermes Agent, Pi and DeepSeek Harness let you pick the wire per provider. T3 Code and Gas Town speak none of these and inherit their child's.

## Pin the model id

Every harness ships a bare OpenAI-style default model name. This API refuses it with `400` and the code `model_id_not_pinned`, on the first request. Accepted forms are `provider/model`, where the part before the first slash names the serving provider, and `profile/` plus a routing profile slug. [Models](/features/models) lists them all.

For a harness, use `unirouter/auto`. It means whichever route your workspace made its default, so the model changes on the Routing screen rather than in a config file. [Routing profiles](/features/routing-profiles) covers it.

```json 400
{
  "error": {
    "message": "The model \"gpt-4o\" does not name its provider. A model field carries either \"provider/model\", where the part before the first slash is a provider this platform serves and the rest is that provider's own id for the model, for example \"anthropic/claude-opus-4-5\", or \"profile/{identifier}\", one of your workspace's routing profiles, for example \"profile/fast\". GET /v1/models lists the exact strings this key can call.",
    "type": "invalid_request_error",
    "param": "model",
    "code": "model_id_not_pinned",
    "request_id": "00000000-0000-4000-8000-000000000000"
  }
}
```

Each harness needs one edit, in a different place. A harness with several models (main, commit messages or titles, applying edits) needs each pinned. A harness with a fixed dropdown of vendor names cannot take this id shape, and its page says so.

## Embeddings are not served yet

Embeddings are not served yet, and we have no date to give. `POST /v1/embeddings` is refused with a 404 `not_found_error`.

Features that index your repository by meaning call an embeddings endpoint. These are codebase indexing, retrieval over ingested documentation, memory that recalls earlier sessions by similarity, and reranking. Harnesses that read files, grep, walk the syntax tree or ask a language server do not need one.

Each harness page says whether it calls no embeddings endpoint, has an embeddings role to point elsewhere, or has no embeddings feature in its own documentation. If a harness sets its embedding model separately, leave that setting alone and change only the chat model.

## A harness spends faster than a chat client

Credit is prepaid, and a harness usually reaches the account spend rate cap before the balance. **The cap counts credit held, not credit spent.** A request's hold is its own `max_tokens`, or else the model's published maximum output length. Nothing comes back out of the window, so a cheap request still counts for its full 60 seconds.

A harness fires several requests at once, often without `max_tokens`. Each holds the whole published maximum, so the cap can refuse it while real spend is a fraction of that. The refusal is `429` with `spend_rate_exceeded`, and it clears 60 seconds after the earliest hold.

**The lever is `max_tokens`.** Set a realistic output ceiling wherever a harness exposes one. You get more requests a minute from the same cap, at the same charge. [Rate limits and spend controls](/manage/spend-controls) covers the cap and which limits you can raise.

### Running out part way through a session

A request started when the workspace cannot cover its hold is refused with `402` and `insufficient_credit`. Nothing is charged.

A stream already running when the credit runs out is cut. Its terminating line carries `insufficient_quota` and `balance_exhausted`, and you are charged for what was produced. There is no `data: [DONE]`. [Streaming](/features/streaming) documents the line and the other codes that end a stream.

**Do not retry a `402`.** The condition is a balance, so waiting changes nothing. Take `402` off any retry list you control. The way out is buying credit.

## Every turn is its own billed request

A harness is a tool-calling loop. It sends tool definitions, the model asks for a tool call, and the harness runs it locally and resends the conversation with the result.

Your request is forwarded as sent, and `tool_calls` come back unchanged. **Nothing is executed on our side.** The harness runs each tool on your machine, under your approvals.

**Each turn is a separate billed request and its own row in [Activity](/manage/usage-and-metering).** Each resends a slightly longer conversation, so one instruction can become a dozen rows. That is a session, not a metering fault.

## Prompt caching is worth having here

A harness resends a large, stable prefix every turn. Provider caching passes through, and cache reads and writes are priced as their own token kinds. [Models](/features/models) covers those rates. There is nothing of ours to switch on. Whether your harness sends what a provider needs to cache is a question about the harness.

## Keys, and where they must not go

Harness config often lives in the repository. Read the key from the environment where the harness supports it, and check each file before you commit it. At least two harnesses here have a project-local config designed to be checked in.

**Do not assume `OPENAI_API_KEY` and `OPENAI_BASE_URL` work.** A harness is not an SDK, and none of these takes its base URL from `OPENAI_BASE_URL` on the documented path. Hermes Agent reads that variable only for its direct OpenAI provider. Each page gives its own key form.

A key is shown once, and we keep only a hash. A workspace holds up to 500. [Authentication](/get-started/authentication) covers minting and revoking. Mint one key per harness, so revoking one costs nothing else.

## Which models to point it at

We do not recommend models, and the catalog moves. Ask for it:

```bash
curl https://api.hopscotchlabs.ai/v1/models \
  -H "Authorization: Bearer ub_live_XXXXXXXXXXXX"
```

Check `capabilities.tools` first. **A model whose `tools` does not read `yes` behaves badly.** It answers in prose instead of a tool call, and the loop stalls or invents file edits in the chat. That looks like unhelpfulness, which makes it worse than a refusal. Check `streaming` as well, and `vision` if you paste screenshots.

## Harnesses we looked at and did not write up

Naming these shows whether a harness is missing on purpose. None has been checked to the standard above, so this is a survey, not a verdict.

**Gas Town presets.** Gemini's CLI, Kiro, Auggie, Amp, GitHub Copilot's CLI and Omp. T3 Code drives Grok's agent. We have not established whether any accepts a custom endpoint.

**Antigravity.** The evidence on an OpenAI-compatible endpoint contradicts itself, and the routes that reach it are third-party proxies. `unknown` stays the answer until someone reads the current release.

**Kilo Code and Roo Code.** Same family as [Cline](/integrations/cline), with the same kind of provider block. Likely to work, and not documented.

## What we did not verify

**Checked.** That a harness has a custom base URL setting, its name, whether it appends `/v1`, whether its model field accepts any string, and which endpoints its features call. Each per-harness page names its source and date.

**Not checked.** That a session against this API succeeds. No harness has been run end to end, because the hostname every page prints is not the settled customer hostname yet. Harness configuration churns faster than documentation, so a setting that has moved since a page's date is likelier than one that never existed.
