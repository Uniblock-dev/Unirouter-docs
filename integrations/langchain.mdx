LangChain's `ChatOpenAI` wraps the official OpenAI SDK, so it inherits that SDK's base URL behaviour and adds a naming layer of its own. The two language versions spell the setting differently, and the framework carries a default model. Get both right first.

## Python

```python
import os
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="openai/gpt-4o-mini",
    base_url="https://api.hopscotchlabs.ai/v1",
    api_key=os.environ["HOPSCOTCH_API_KEY"],
)

print(llm.invoke("Say hi in five words.").content)
```

`base_url` and `api_key` are the canonical arguments. Both are pydantic aliases for `openai_api_base` and `openai_api_key`, and either spelling works. The environment fallbacks are `OPENAI_API_BASE`, which LangChain reads itself, and `OPENAI_BASE_URL`, which the OpenAI SDK reads when LangChain has not.

## JavaScript

```javascript
import { ChatOpenAI } from "@langchain/openai";

const llm = new ChatOpenAI({
  model: "openai/gpt-4o-mini",
  apiKey: process.env.HOPSCOTCH_API_KEY,
  configuration: {
    baseURL: "https://api.hopscotchlabs.ai/v1",
  },
});

const response = await llm.invoke("Say hi in five words.");
console.log(response.content);
```

**The base URL is nested and the key is not.** `apiKey` is top-level. `baseURL` belongs inside `configuration`, which passes through to the OpenAI client. A top-level `baseURL` is ignored rather than rejected, so a configuration that looks right can still reach OpenAI. If calls are answered by the wrong API, check this line first.

## The default model is the thing that bites

**`ChatOpenAI` carries a default model in both languages, and it is a bare OpenAI id.** The field defaults to `gpt-3.5-turbo`, so a `ChatOpenAI()` with no `model` argument sends a name with no provider in front of it. This API refuses that with `400` and the code `model_id_not_pinned`.

It is the most common first failure here. The error names the model field, and the developer never wrote one. Every construction site needs the argument, including library code and templates you copied. The id forms are on the [integrations overview](/integrations/overview), and [Models](/features/models) lists the exact strings your key can call.

## What else is specific to this framework

**`/v1` belongs in the value.** LangChain passes your base URL to the OpenAI SDK, which appends `/chat/completions` and adds no `/v1`. The same in both languages.

**Recent Python versions send `stream_options` even to a custom base URL.** `ChatOpenAI` has a `stream_usage` setting that asks for token counts in the stream. Its documentation records that `langchain-openai` `0.3.35` changed this: it used to be off for a custom base URL or client, and is now on. The body is forwarded as sent, so the provider decides what it does with the option. If a provider rejects it, set `stream_usage=False`.

**Embeddings are not served here yet.** `OpenAIEmbeddings` is a separate class that posts to `/embeddings`. This API does not serve [`POST /v1/embeddings`](/features/completions-and-embeddings#embeddings) yet, and has no date to give. A vector store, retriever or memory built on that class cannot use this base URL for embeddings. Point that class at a provider you call directly.

**Nothing calls the catalog.** `ChatOpenAI` does not ask `GET /v1/models` to validate a model name, in either language.

**The library warns against third-party endpoints.** Its documentation says `ChatOpenAI` targets the official OpenAI specification, and that extra fields from other providers are not extracted. Our responses are the OpenAI chat completion shape. The extra things we carry ride on response headers and an SSE comment line, not in the body. See [OpenAI compatibility](/get-started/migrate-from-openai).

## Where the request id is

LangChain's Python package wraps the SDK's exceptions in subclasses that inherit from both the SDK exception and a LangChain error type. `OpenAIAuthenticationError` is an `openai.AuthenticationError`, built with the original `response` and `body`. An `except openai.APIError` you already have keeps catching, and the request id is where it was:

```python
import openai

try:
    llm.invoke("Say hi in five words.")
except openai.APIStatusError as error:
    body = error.response.json()["error"]
    print(error.status_code, body["type"], body["code"], body["request_id"])
```

On success, Python's `ChatOpenAI` takes `include_response_headers=True`, which puts response headers in `response_metadata["headers"]`, so `x-hopscotch-request-id` and `x-request-id` are readable. It is off by default.

## What we did not verify

**Checked.** The Python arguments and their aliases, the two environment fallbacks, the Python default model of `gpt-3.5-turbo`, the JavaScript nesting and its default, the `stream_usage` change and its release, that `OpenAIEmbeddings` defaults to an OpenAI embedding model, that the wrapped exceptions keep `response` and `body`, and that neither class calls the catalog. These come from the `langchain-ai/langchain` and `langchain-ai/langchainjs` sources on their default branches.

**Not checked.** That a call configured this way succeeds against our hostname. Nothing here has been executed, because the base URL this site prints is not yet a host that answers.

**Not checked either.** Which LangChain flows reach `OpenAIEmbeddings` by default. We read that the class exists, but did not trace which vector store, memory or retriever defaults pull it in. The paragraph above names the class that cannot use this base URL, not the flows that reach it.

**And not checked.** What a provider does with the `stream_options` that recent Python versions send. We forward the body as sent, and have not run it to find out.
