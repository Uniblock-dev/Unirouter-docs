Every framework here works for the same reason: each already has an OpenAI-compatible provider, because each already talks to OpenAI. Point that provider at our base URL with a Hopscotch key, and the framework needs to know nothing else has changed.

<BaseUrl />

## The one required change

**Every model id must include its provider.** Use `openai-main/gpt-4o-mini`, for<br /> example, rather than `gpt-4o-mini`. A bare id gets a `400` with the code `model_id_not_pinned`. The error lists the accepted formats and points you to `GET /v1/models`. Its type is `invalid_request_error` with `param` set to `model`, so your existing error handling can parse it.

If you move an app over without changing its model ids, every request fails with this error, so you'll notice right away.

This needs extra care with frameworks, because **some frameworks have a default model built in**. Even if you never set a model, the framework sends one, and it's a bare OpenAI id. Each framework's page says whether it does this. [Models](https://docs.hopscotchlabs.ai/features/models.md) explains the id format, and [Migrate from OpenAI](https://docs.hopscotchlabs.ai/get-started/migrate-from-openai.md) covers the rest of the switch.

## The surface a framework can reach

Because only chat completions and the model catalog are available, two things change. Each framework's page covers whichever applies to it:

- **Frameworks that default to another API are set to chat completions.** Two libraries here, the Vercel AI SDK and Pydantic AI, now send their default OpenAI setup to the Responses API. Their pages set chat completions explicitly, since that default has already changed once.
- **Embeddings aren't available.** If a framework uses embeddings to build an index, retriever or memory, those calls fail. You won't see the error when you configure the framework, only when that code first runs. If a framework uses embeddings by default, as LlamaIndex does, its page tells you what to set instead.

See [OpenAI compatibility](/get-started/migrate-from-openai) for the endpoint table and the requests we refuse.

## What every one of these pages assumes

- **The base URL carries `/v1` and nothing after it.** Every library appends `/chat/completions`, so `https://api.hopscotchlabs.ai/v1` is the value. Without `/v1` you get a `404`, not a helpful message.
- **The key comes from the environment.** A Hopscotch key spends real credit, so no example holds it in source.
- **Nothing Hopscotch-specific goes in the request.** Only `Authorization` and `Content-Type` are read, and `x-uniblock-*` is stripped inbound. A framework's custom-header option cannot change how a request is served.

## What we did not verify

**Checked.** That each framework exposes a base URL setting, its name, its type and the object it belongs to. Each page names the library documentation or source it was read from. These are facts about public libraries, checkable where we did.

**Not checked.** That a call configured this way succeeds against our hostname. No example here has been executed end to end, and DOCS_PLAN's runnability rule is why each page says so. The base URL this site prints is not yet a host that answers. When that lands, these pages get a transcript and this callout changes.

**Also not checked.** Library behaviour over time. Every fact was read from a current version of a library we do not control, and any can change. Where a library has already changed one of these settings, the page says which version the fact belongs to.
