Every framework here works for the same reason: each already has an OpenAI-compatible provider, because each already talks to OpenAI. Point that provider at our base URL with a Hopscotch key, and the framework needs to know nothing else has changed.

<BaseUrl />

## The one change that is not optional

**Every model id names its provider.** `gpt-4o-mini` is not a model id here. `openai/gpt-4o-mini` is. A bare id is refused with `400` and `model_id_not_pinned`. The refusal names the accepted forms and points you to `GET /v1/models`. It arrives as `invalid_request_error` with `param` set to `model`, so your error handling parses it.

This breaks an untouched application, loudly. It matters more in a framework, because **some frameworks carry a default model of their own**. A framework you never told which model to use still sends one, and it is a bare OpenAI id. Your framework's page says whether yours does. [Models](/features/models) covers the id forms, and [Migrate from OpenAI](/get-started/migrate-from-openai) covers the rest of the move.

## The surface a framework can reach

The documented API is `POST /v1/chat/completions` plus the catalog reads, `GET /v1/models` and `GET /v1/models/{id}`. That is what these pages configure, and it is the whole of what they claim.

Two consequences, each noted on the relevant page:

- **A framework whose default path is not chat completions is pinned to chat completions.** Two libraries here now reach for OpenAI's Responses API by default. These pages pin chat completions explicitly rather than trusting a default that has moved once.
- **Embeddings have no home here.** A framework that reaches for embeddings to build an index, retriever or memory will not get them. The failure arrives when that code path first runs, not at configuration. Where a framework does this by default, its page says so and what to set instead.

See [OpenAI compatibility](/get-started/migrate-from-openai) for the endpoint table and refusals.

## What every one of these pages assumes

- **The base URL carries `/v1` and nothing after it.** Every library appends `/chat/completions`, so `https://api.hopscotchlabs.ai/v1` is the value. Without `/v1` you get a `404`, not a helpful message.
- **The key comes from the environment.** A Hopscotch key spends real credit, so no example holds it in source.
- **Nothing Hopscotch-specific goes in the request.** Only `Authorization` and `Content-Type` are read, and `x-uniblock-*` is stripped inbound. A framework's custom-header option cannot change how a request is served.

## What we did not verify

**Checked.** That each framework exposes a base URL setting, its name, its type and the object it belongs to. Each page names the library documentation or source it was read from. These are facts about public libraries, checkable where we did.

**Not checked.** That a call configured this way succeeds against our hostname. No example here has been executed end to end, and DOCS_PLAN's runnability rule is why each page says so. The base URL this site prints is not yet a host that answers. When that lands, these pages get a transcript and this callout changes.

**Also not checked.** Library behaviour over time. Every fact was read from a current version of a library we do not control, and any can change. Where a library has already changed one of these settings, the page says which version the fact belongs to.
