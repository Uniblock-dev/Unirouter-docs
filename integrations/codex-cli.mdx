[Codex CLI](https://developers.openai.com/codex) is OpenAI's terminal coding agent, configured by one TOML file. It is why this API serves the Responses endpoint at all, and the only harness here that cannot use chat completions. Read [coding harnesses](/integrations/coding-harnesses) first.

## It speaks the Responses API and nothing else

The `wire_api` key accepts one value, `responses`. The string `chat` is a startup error naming the removal, not a fallback. Codex posts to [`POST /v1/responses`](/api-reference/openapi.public.json). Everything below the door is shared with chat completions: the same key, catalog, balance holds and usage rows.

## The configuration surface

The file is `~/.codex/config.toml`, with an optional project-scoped `.codex/config.toml`:

```toml ~/.codex/config.toml
model_provider = "hopscotch"
model = "unirouter/auto"

[model_providers.hopscotch]
name = "Hopscotch"
base_url = "https://api.hopscotchlabs.ai/v1"
env_key = "HOPSCOTCH_API_KEY"
wire_api = "responses"
```

```bash
export HOPSCOTCH_API_KEY=ub_live_XXXXXXXXXXXX
```

**`base_url` must include `/v1`.** Codex appends only `/responses`, so a bare hostname receives a `404`. This is the opposite of Claude Code's convention.

**Do not name the provider `openai`.** Built-in provider ids are reserved, and a block with that name is ignored rather than refused. Any other id works.

## The key comes from a variable you name

`env_key` names the variable Codex reads, at request time. Nothing reads `OPENAI_API_KEY` unless you point `env_key` at it. Codex's login flow writes `~/.codex/auth.json`, which belongs to the built-in OpenAI provider. Leave it alone and use `env_key`.

## Pin the model id

Codex's `model` field is free text, and this API needs a provider in it, so change the default before the first request. Accepted forms are on [Models](/features/models). For a harness, `unirouter/auto` is the one to use, because the model changes on the Routing screen rather than in a TOML file. [Routing profiles](/features/routing-profiles) covers it.

A provider-pinned id works too. Codex's picker does not always list an id containing a slash, and it has been reported overwriting a custom provider's selection. Setting `model` in the file avoids both. `review_model`, which `/review` uses and which defaults to the session model, takes the same pinning.

## `store` is refused on the platform's own provider keys

The Responses API defaults to storing responses at the provider. On the platform's own provider keys, `store: true` is refused before admission with `400`, `code` `null` and `param` set to `store`. An omitted `store` is sent as `false`. Nothing is held and nothing reaches a provider. On your own provider key, `store` is forwarded as sent.

Codex sends `store: false`, so this does not affect it. It matters for your own wrapper or script. The fields refused on the platform's keys are listed on [Request parameters](/api-reference/parameters#the-fields-refused-on-the-platforms-own-provider-keys).

## Parameters Codex sends are forwarded

A Codex request carries `reasoning`, `verbosity`, `service_tier`, `prompt_cache_key`, `include` and `parallel_tool_calls`. Your body is forwarded as sent, and none is rewritten.

The one caveat is `service_tier`. On the platform's own keys, a tier other than `auto` or `default` is refused with `400` and `param` set to `service_tier`, because this platform does not meter priority or flex pricing yet. On your own key, any tier is forwarded.

A provider that rejects a field answers with its own refusal, relayed with its sentence quoted. `model_reasoning_effort`, `model_verbosity` and `model_supports_reasoning_summaries` decide whether those fields are sent, and they are the levers when a model rejects one.

## There is no output ceiling to set

Codex has no maximum-output setting. `model_context_window` is an input-side figure, and `model_auto_compact_token_limit` sets when a conversation is compacted, not how long a reply may be.

A request naming no output ceiling holds the model's whole published maximum against your spend rate cap, so Codex can reach that cap while real spend is a fraction of it. [Rate limits and spend controls](/manage/spend-controls) covers what the cap counts.

## No embeddings

Codex builds context by reading and searching files and by compacting conversations. Its client calls no embeddings endpoint, so the failure modes on [coding harnesses](/integrations/coding-harnesses) do not apply to it.

## What we did not verify

- That a Codex session against this API succeeds. Nothing was run.
- Whether Codex validates the `model` string outside the provider path. We read the provider code and found no allowlist there, but did not trace the whole resolution path.
- The schema of `model_catalog_json`, the documented way to declare a custom model's metadata, which may fix the `/model` picker behaviour above.
- Whether `model_supports_reasoning_summaries` suppresses the `reasoning` field entirely or only its summary half.
- Codex has an open report of requests failing against non-OpenAI Responses endpoints while the same body sent by hand succeeds (`openai/codex#24973`). It has no upstream diagnosis, and we have not reproduced it. If a session fails in a way this page does not explain, check that report before assuming the fault is ours.
