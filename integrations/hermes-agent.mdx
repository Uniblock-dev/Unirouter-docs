## The configuration surface

Hermes has a first-class custom OpenAI-compatible endpoint, so no plugin is needed. The file is `~/.hermes/config.yaml`:

```yaml ~/.hermes/config.yaml
model:
  provider: custom
  default: openai/gpt-4o-mini
  base_url: https://api.hopscotchlabs.ai/v1
  api_key: ub_live_XXXXXXXXXXXX
```

`hermes model`, run outside a session, writes the same fields to the same file. **Hermes does not append `/v1`**, so include it. `model.default` and `model.model` are the same key.

## Prefer the named form

The block above holds the key in the file. The named form can read it from your environment instead:

```yaml ~/.hermes/config.yaml
providers:
  hopscotch:
    api: https://api.hopscotchlabs.ai/v1
    key_env: HOPSCOTCH_API_KEY
    transport: chat_completions
    default_model: unirouter/auto
```

```bash
export HOPSCOTCH_API_KEY=ub_live_YOUR_KEY_HERE
```

`api` is the base URL, and `base_url` and `url` are accepted spellings. `transport` picks the wire, and `chat_completions` is the one this site covers. The wizard sets it explicitly. Switch to the entry inside a session with `/model custom:hopscotch:<model id>`.

A third form, `key_cmd`, runs a command that prints a token and caches it. It suits gateways that issue short-lived bearers, or a vault instead of a shell profile. A Hopscotch key does not expire on a clock, so `key_env` is the simpler choice.

## `OPENAI_BASE_URL` is honoured, and not for this

Hermes reads `OPENAI_BASE_URL`, but only for its `openai-api` provider, its direct OpenAI path. Set it while your provider is `custom` and nothing happens. Set it while your provider is `openai-api` and you have configured a second route by accident. Hermes also removed `LLM_MODEL` from `.env`, and clears stale entries on the next setup or config migration.

## Pin the model id, in more places than one

The pinned-id rule on [coding harnesses](/integrations/coding-harnesses) applies to `default_model`. Put `unirouter/auto` there.

Hermes also routes auxiliary tasks to your main model by default: vision, web summarisation and the compression that shortens long sessions. Each is its own request, and each can be pointed at a different model. Pin those too. Otherwise those tasks fail while the main loop keeps working, which is a confusing shape of failure.

`discover_models` asks the endpoint what it serves. [`GET /v1/models`](/features/models) returns every string your key can call. We did not verify what Hermes does with the reply.

## There is no output ceiling to set

This is the opposite of most harnesses. Hermes has stopped reading an output cap: `model.max_tokens`, `HERMES_MAX_TOKENS` and per-model output overrides are gone, and a custom endpoint receives no automatic cap, so the server's default decides.

So a Hermes request names no `max_tokens`, and holds the model's whole published maximum against your spend rate cap. Nothing on the harness side fixes that. [Rate limits and spend controls](/manage/spend-controls) covers the account side. `context_length` on the provider entry sizes the conversation window and decides when history is compressed. It does not limit what is held.

## One instruction can be many sessions

Hermes has two multipliers on the ordinary tool loop.

**Delegation.** Hermes dispatches subagents to run workstreams in parallel. Each is its own conversation on the same key, so a fan-out multiplies rows.

**Its own task board.** Hermes ships a kanban feature with worker lanes: several agents drawing work without a person in each turn. With no output ceiling, that is the configuration most likely to meet a `429` with `spend_rate_exceeded`.

## Memory is where the embeddings are, and it is already separate

Some Hermes memory providers embed. Their backends configure their own embedder, in the memory provider's own file rather than in `model` or `providers`. For the open-source path, the documented choices are OpenAI and Ollama.

Point the chat model here and change nothing about memory. This API does not serve embeddings yet, so do not point a memory embedder at it.

## Keys, and the file that gets committed

Keep the key in your environment or in `~/.hermes/.env`, both outside your repository. `AGENTS.md`, which Hermes reads as project instructions, is meant to be committed. It holds instructions, not credentials, so it is a trap only if you put a key there.

Mint a key for Hermes rather than reusing one. [Authentication](/get-started/authentication) covers minting and revoking.

- What `transport: codex_responses` sends. [Codex CLI](/integrations/codex-cli) documents the Responses endpoint this API serves, but we did not trace what Hermes sends under that name.
- What Hermes does with the `discover_models` reply, or whether a discovered id is sent as the `model` field byte for byte. A mismatch shows as `400` with `model_id_not_pinned` or `404` with `model_not_found`, and neither costs anything.
- Whether an auxiliary task sends an output cap of its own when the main loop does not. Hermes calls internal bounded tasks an implementation detail.
- Prompt caching from Hermes. Provider caching passes through this API, but whether Hermes sends what a provider needs is a question about Hermes.
