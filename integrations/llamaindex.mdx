LlamaIndex has two OpenAI classes, and the difference matters more here than anywhere else in this section, because the wrong one fails before a request is sent. Its defaults for the language model and the embedding model both fail against this API: the language model default is a bare model name this API refuses, and the embedding default posts to an endpoint this API does not serve yet.

## Use OpenAILike

```python
import os
from llama_index.llms.openai_like import OpenAILike

llm = OpenAILike(
    model="openai/gpt-4o-mini",
    api_base="https://api.hopscotchlabs.ai/v1",
    api_key=os.environ["HOPSCOTCH_API_KEY"],
    is_chat_model=True,
    context_window=128000,   # take the model's real window from GET /v1/models
)

print(llm.complete("Say hi in five words."))
```

`OpenAILike` is described by its own documentation as a thin wrapper that makes the OpenAI model compatible with third-party OpenAI-compatible APIs. That is this API, so this is the class to use.

**The setting is called `api_base`, not `base_url`.** This is the one place in this section where the name differs from the SDK's. LlamaIndex translates it when it builds the client, and the environment fallback is `OPENAI_API_BASE`. The key is `api_key`, falling back to `OPENAI_API_KEY`. The `/v1` belongs in the value.

**`is_chat_model=True` is not optional.** It defaults to `False` on this class, and a model that is not told it is a chat model will not send a chat completion. Set `is_function_calling_model=True` as well if you want tool calling.

## Why the plain OpenAI class does not work

`llama_index.llms.openai.OpenAI` also takes `api_base`, so it looks like it should work. It fails on our model ids. Its `metadata` property looks the name up in a dictionary of official OpenAI model names and raises `ValueError` for anything absent:

```python
if modelname not in ALL_AVAILABLE_MODELS:
    raise ValueError(f"Unknown model {modelname!r}. Please provide a valid OpenAI model name...")
```

Every model id here is a `provider/model` pair, so none is in that dictionary. The class refuses `openai/gpt-4o-mini` even though it would accept `gpt-4o-mini`. The refusal is a `ValueError` raised in your own process, not a `400` from us. LlamaIndex reads `metadata` during a call, so it surfaces from an ordinary `complete` or `chat`, not at construction.

`OpenAILike` avoids this. It overrides `metadata` and uses the `context_window`, `is_chat_model` and `is_function_calling_model` you pass, with no lookup.

## Embeddings, which are the other thing to set

**This API does not serve embeddings yet, and we have no date to give.** `Settings.embed_model` resolves lazily. If you never set it, LlamaIndex builds its own default `OpenAIEmbedding`, which resolves its own key and base URL separately from your `OpenAILike` model. With only that configuration it does not reach this API, and indexing can fail on a missing OpenAI key instead. If you point an embedding model here, [`POST /v1/embeddings`](/features/completions-and-embeddings#embeddings) is refused with a 404 `not_found_error`.

Set `Settings.embed_model` explicitly to a provider you call directly, and keep `Settings.llm` on this API. The default language model is also resolved lazily, as a plain OpenAI client. Setting `Settings.llm` stops that default being built behind you. Skip it and you get the hardcoded-model-list failure above from code you did not write.

## Where the request id is

LlamaIndex calls the OpenAI SDK directly and does not appear to wrap its exceptions. The request id is where the SDK puts it: `error.request_id` on `openai.APIStatusError`, read from the `x-request-id` header. The [Python SDK page](/integrations/openai-sdk-python) has the details. Retries are LlamaIndex's own, through a decorator that decides when to retry and does not change the failure.
