[Aider](https://aider.chat) is a terminal pair-programming CLI. It configures more than one model, and its repository map needs no embeddings, so it is one of the harnesses least likely to hit the missing endpoint. Read [coding harnesses](/integrations/coding-harnesses) first.

## The configuration surface

Aider takes the base URL as a flag or from the environment:

```bash
export OPENAI_API_BASE=https://api.hopscotchlabs.ai/v1
export OPENAI_API_KEY=ub_live_YOUR_KEY_HERE
```

The flag is `--openai-api-base`, and its own variable is `AIDER_OPENAI_API_BASE`. Aider's documentation names `OPENAI_API_BASE`, not `OPENAI_BASE_URL` (which the official SDKs read). Only the first is documented here, so set that one.

**Include the version segment in the value.** Aider's documentation gives no example for a compatible endpoint, so this follows from the mechanism: the endpoint path is appended to what you give it. A reported version dropped the segment and answered `404`. If every request returns `404` with `endpoint_not_supported`, print the path Aider calls before blaming the key or the model.

## The three models

This is the edit people miss. Aider configures up to three models separately, and each needs its own pinned id:

| Setting | What it does |
|---|---|
| `--model` | The main model. |
| `--editor-model` | Applies edits in architect mode, where the main model proposes them. |
| `--weak-model` | Commit messages and chat-history summaries. |

In some configurations `--weak-model` and `--editor-model` fall back to defaults rather than your main model. A default is a bare vendor name, refused with `model_id_not_pinned`. Set all three if you use architect mode or let Aider write commit messages.

## The model id, and the prefix collision

Aider names a model on a compatible endpoint with an `openai/` prefix. That prefix selects the adapter in the library underneath Aider and is consumed, with the rest forwarded.

Our ids begin with their provider, and for OpenAI-served models that provider is `openai`. So a pinned id and Aider's prefix produce a doubled first segment:

```bash
aider --model openai/openai/gpt-4o-mini
```

**We did not verify what reaches the wire in that case.** The library's issue tracker shows doubled prefixes handled inconsistently, so we will not say which segment survives. You can find out in one request. A `400` with `model_id_not_pinned` means one segment arrived. A `404` with `model_not_found` means both did. Neither costs anything. An id whose provider is not `openai` does not have this problem.

## The repository map does not use embeddings

Aider builds its repository map from a parser and a graph ranking over your source. It calls no embeddings endpoint, and the project has never shipped an embeddings index. Aider needs nothing configured for it.

## Two things that spend credit quietly

**Prompt caching is provider-specific, and keepalive pings are requests.** `--cache-prompts` is off by default and names specific vendor families, so whether it helps depends on the pinned model. `--cache-keepalive-pings` sends periodic requests to keep a cache warm. Each one is billed and recorded in [Activity](/manage/usage-and-metering).

**Aider does not enforce token limits.** It reports the provider's limit errors rather than pre-empting them. For a model it does not recognise, it assumes an unknown context window and no cost, and warns once. Ours is unrecognised, so expect that warning and an empty or wrong cost display. Supply the missing figures with `.aider.model.metadata.json` or `--model-metadata-file`, taking the context window and maximum output from [`GET /v1/models`](/features/models), which publishes both.

## Keep the key out of the repository

Aider reads `.aider.conf.yml` and `.env` from your home directory, repository root and current directory, in that order, with later files overriding. Two of those three locations are inside the repository. Keep the key in the home-directory copy or the environment variables above.

## What we did not verify

- That an Aider session against this API succeeds. Nothing was run.
- What model string reaches the wire for a doubled provider prefix. The way to find out is above.
- Whether `--list-models` queries this API or the library's local model database. Its wording suggests the local database, so ask `GET /v1/models` for our catalog.
- Whether Aider honours `OPENAI_BASE_URL` as well as `OPENAI_API_BASE`. Only the second is documented, so only the second is written above.
- Whether the `openai` adapter can call anything other than chat completions. We found no documentation either way. This API serves only chat completions among the inference endpoints, so a configuration that reached another would answer `404`.
