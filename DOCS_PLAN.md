## 1. Executive summary

Uniblock Gateway is an OpenAI-compatible LLM router. A developer changes one base URL (`https://ai.uniblock.dev`) and one API key, keeps their existing OpenAI SDK, and calls models across providers on one prepaid balance. The fee is 2.5% (250 basis points), taken **at credit purchase**; a served request deducts the provider's rate at face value with no markup (`SRC/_bmad-output/product/decisions/the-platform-fee-is-taken-at-purchase.md`).

The docs site has three jobs:

1. **Make the two-line migration true in practice**: quickstart, OpenAI-compatibility notes, auth, errors, streaming.
2. **Document the money model honestly**: prepaid credit, fee at purchase, no per-request markup, usage visibility, spend controls.
3. **Document the workspace model**: keys, members, roles, the playground, and the owner-only money rule.

The hard constraint shaping everything: **the product is partially built.** The plan below marks every page `WRITE-NOW`, `PARTIAL` (write to shipped behavior only, with named gaps), or `BLOCKED` (do not publish until a named story/decision lands). Docs must never claim unshipped behavior; `SRC/_bmad-output/build/sprint-status.yaml` is the arbiter of "shipped".

## 4. Audiences and journeys

**A1. The migrating developer (primary).** Modeled on the PRD's "Priya": already calls OpenAI directly, evaluates on price and effort. Journey: land on Overview → Quickstart (swap base URL + key, first request in under five minutes) → OpenAI compatibility page (what works, what differs, what is not supported) → Errors and streaming when something surprises them. Success: first 200 from `POST /v1/chat/completions` with their existing SDK.

**A2. The evaluating stranger (signed-out).** PRD FR-43 and Epic 8: evaluates on the model catalog and price without an account. Journey: Overview → Models and pricing concept page → Credits page (the 2.5%-at-purchase story) → sign-up. Note: the in-app public catalog (Epic 8.1-8.8) is unbuilt, so the docs describe the pricing *model* and defer live prices to the product (§14, OQ-13).

**A3. The workspace operator.** The person who runs the account day to day: buys credit, invites members, sets spend controls, reads Activity. Journey: dashboard guides (keys, billing, members, spend controls, usage). Often the workspace **owner**, the only role that touches money.

**A4. The team member (developer/viewer role).** Reads balance and usage, uses the playground and keys they can see, cannot touch billing. Docs must state role boundaries wherever an action is role-gated, using the product's own refusal language.

**A5. Support-seeking customer.** Arrives from an error. Journey: error code → the errors reference → the specific concept page (rate limits, credit) → quote `request_id` to support. Every error-adjacent page ends with the request-id support note (shared snippet).

Explicit non-audiences: Uniblock staff (the console is internal, Cloudflare Access-gated); self-hosters (§10: the product is hosted-only); contributors to the source repo.

## 8. API reference strategy (OpenAPI)

**Decision: publish a derived public spec, never either repo spec verbatim.**

- `SRC/services/gateway/openapi.json` is **internal-only**. It documents the fork's whole surface (catch-all proxies, Anthropic routes, files/batches/audio, `x-uniblock-config` mechanics) which is not the customer contract, carries workers.dev hostnames, declares no auth (the gateway sits behind a service binding), and self-describes as "close-but-not-contractual". Publishing it would document endpoints customers cannot reach and reveal internal topology.
- `SRC/services/control-plane/openapi.json` is the source, but it covers four surfaces (`/admin`, `/api/me`, `/internal`, `/v1`). Only **`/v1`** is the public API-key product. `/api/me` is the dashboard's private API (documented in prose guides, not as a reference; it is session-cookie-bound and not a supported integration surface). `/admin` and `/internal` and `/webhooks/stripe` are never published.

**The artifact**: `api-reference/openapi.public.json`, produced by a filter script (§16) that:

1. Starts from `SRC/services/control-plane/openapi.json`.
2. Keeps only `paths` under `/v1` (today: `POST /v1/chat/completions`, `GET /v1/models`) plus referenced components.
3. Keeps only the `customerApiKey` security scheme; strips `staffAccess`, `internalSecret`, `sessionCookie*`, `stripeSignature`.
4. Rewrites `servers` to exactly `[{"url": "https://ai.uniblock.dev", "description": "Production"}]`; strips localhost and workers.dev entries.
5. **Injects the header documentation the source spec lacks** (the api-scout finding: neither spec documents `x-uniblock-usage`, request-id headers, or the 402/429 money statuses): response headers on `/v1/chat/completions` (`x-uniblock-request-id`, `x-uniblock-usage`, diagnostics), and the 401/402/429/404/5xx responses with the OpenAI envelope schema from `openai.ts`. These injections live in a checked-in overlay file (`api-reference/overlay.public.json`) so the pipeline is reproducible: base spec + overlay = artifact.
6. Fails the build if a kept path has no `example`, or if the base spec added a `/v1` path the overlay does not classify (forcing a human decision per new route).

Upstream contribution to flag to the source-repo owner (not done by docs writers): the money statuses and custom headers belong in the source spec itself under its "spec moves with the code" rule; when that lands, the overlay shrinks.

Mintlify wiring: `docs.json` `api.openapi` points at the artifact; endpoint MDX pages are generated with the interactive playground pointed at production. The playground makes real, billed requests; each endpoint page carries a shared callout snippet saying exactly that (requests spend real credit).

## 13. Customer-facing vs internal: the must-not-publish register

**Redirects**: none at launch (greenfield site). Standing rule: once published, a path is permanent; moves ship with a `redirects` entry in docs.json in the same PR (CI check, §16). Reserve stable prefixes now (`/api-reference/*`, `/concepts/*`, `/guides/*`, `/get-started/*`, `/resources/*`) so growth never forces a move.

**SEO**: every page carries frontmatter `title` (verb-led for guides, noun-led for concepts) and `description` (one sentence, under 160 chars, stating the page's claim, not marketing). The phrase to own organically: "OpenAI-compatible LLM router" plus "base URL" migration terms; the index and compatibility pages carry them naturally. `noindex` on nothing (all pages are public by design); sitemap and canonical handled by Mintlify defaults once the hostname exists (§14 item 9). No structured-data investment in v1.

**Accessibility**: inherits the product's floor (EXPERIENCE.md): color never carries meaning alone (callout icons + labels, not tint alone); contrast follows the token system (ink blue for links, never brand blue on white); all images get alt text describing the claim the image makes, not "screenshot"; code blocks never encode meaning in color alone (annotate SSE transcripts with comments); tables have header rows; heading hierarchy strict (one h1 via frontmatter, no skipped levels). Acceptance: `mintlify broken-links` clean plus a manual keyboard-nav pass on the two tab bars per release.

## 16. Validation scripts and CI

All scripts live in `scripts/` in this repo; CI is one GitHub Actions workflow (`.github/workflows/docs-ci.yml`) running on every PR. (Files are created during implementation, not by this plan.)

1. **`scripts/build-public-openapi.mjs`** — the §8 filter+overlay pipeline. Inputs: a checked-in copy of the control-plane spec (synced deliberately, see 2) + `overlay.public.json`. Fails on: unclassified new `/v1` path, missing examples, non-production server leakage, any `/admin|/internal|/api/me` path surviving the filter.
2. **`scripts/sync-source-spec.mjs`** — run manually/on schedule against a checkout of the source repo: copies `services/control-plane/openapi.json` in and prints a diff of `/v1` paths. Docs never read the source repo at CI time (it is private and moves); the checked-in copy is the reviewed sync point, and the diff is the writer's change signal.
3. **`scripts/lint-banned-content.mjs`** — greps all MDX + the public spec for the §13 register: banned words (Portkey, fork, workers.dev, wrangler, Durable Object, the internal header names, staff capability names, "absorbed cost", "strain", competitor pricing comparisons), banned URL patterns (`*.workers.dev`, `staging-*`), and em/en dashes in prose. Maintained as `banned-content.yml` with a per-entry reason so the list explains itself.
4. **`scripts/check-claims.mjs`** — the §13 numeric-claims registry check.
5. **`scripts/check-status-gates.mjs`** — every page carries frontmatter `status: write-now|partial|blocked` and `gates: [story-ids]`; the script fails if a `blocked` page is in docs.json navigation, and prints `partial` pages' gates for the release checklist. This is how "docs never claim unshipped behavior" becomes mechanical rather than remembered.
6. **`mintlify broken-links`** + `mintlify dev` build — link integrity and valid MDX/docs.json.
7. **Example verification (manual, gated)**: PR template requires a pasted transcript for any changed code example (§9 runnability rule). Not automated in v1 (would need live credentials in CI, which this plan declines).

CI order: build-public-openapi → mintlify build → banned-content → claims → status-gates → broken-links. Any failure blocks merge.
