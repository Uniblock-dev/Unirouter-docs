The body of a chat completion is OpenAI's, and it travels to the provider as you
wrote it. This page says exactly which parts of it this platform looks at, which
parts it changes, and what happens to everything else.

## What we read

Before we send your request, we read two fields to work out what it could cost. Reading them doesn't change them.

| Field | Why we read it |
| :-- | :-- |
| `model` | To find the provider and the rate, and to check that we can serve the model. |
| `max_tokens` or `max_completion_tokens` | To decide how much credit to hold while the request runs. If you send both, we use the larger value. |

If we can't make sense of a value, the two fields are handled differently:

- **An output ceiling we can't read** is treated as missing. We hold credit at the model's published maximum output, leave the value in your body, and let the provider respond to it.
- **A missing or malformed** `model` is refused before any provider is called, because we can't continue without it. Both refusals name a `param`, which is how you tell them apart from provider errors.

## What we change

These changes apply on every key. We list them all so you never have to discover a changed body from a provider's error message.

- `model`**, when you name a route.** Sending `profile/{identifier}` or `unirouter/auto` asks us to try a list of models in order. Each attempt reaches the provider with the ID of the model being tried. See [Routing profiles](https://docs.hopscotchlabs.ai/features/routing-profiles.md).
- `max_tokens`**, when the provider requires it.** Some providers refuse requests that don't include `max_tokens`. If your body has neither `max_tokens` nor `max_completion_tokens` and the provider is one of these, we add `max_tokens` set to the model's published `max_output_tokens`. That's the same figure we were already holding credit against. If you set a ceiling yourself, we keep it. Provider-specific translation still runs after this step.
- `store `**on Responses.** If you leave out `store` on `POST /v1/responses`, we send `store: false`.
- **Routing fields on chat completions.** We remove `provider`, `models` and `transforms`, which are fields reseller providers read. Clients that send them keep working, and you're charged for the model you named.
- **Vertex Gemini fields.** We translate OpenAI-compatible fields into Google's request format. For example, `max_tokens` sets the output limit, `reasoning_effort` picks a thinking level, and `modalities` and `image_config` control image output on supported chat models. See [Gemini on Vertex](https://docs.hopscotchlabs.ai/features/vertex-gemini.md) for request and response shapes.

On the platform's own provider keys, some fields are also blocked.

## Everything else is forwarded

For providers with an OpenAI-compatible pass-through API, any other parameter you send can reach the provider unchanged.

Native APIs such as Vertex Gemini work differently. Only the fields we map reach the native request, and the values each model accepts vary.

Two things to plan for:

- **Published model metadata isn't an allowlist.** If a parameter is missing from it, we won't refuse your request for that reason.
- **The provider can still refuse a parameter or value.** We can also reject a value while translating it for a provider's native API, before the request is sent.

### What we refuse ourselves

- **An empty** `reasoning_effort`**.** An empty or whitespace-only value returns `400` with `code: "invalid_value"` and `param: "reasoning_effort"`. No provider accepts it, so we save you the round trip.
- **Some Gemini** `reasoning_effort `**values.** Gemini translation rejects `0` and `false`, and rejects `"minimal"` on models that don't allow that thinking level. These errors include `param: "reasoning_effort"`. Google can still refuse other values. See [Reasoning models](https://docs.hopscotchlabs.ai/features/reasoning.md).
- **Certain fields on platform provider keys.** These are refused on the platform's keys and forwarded on yours. See [the next section](#fields-blocked-on-platform-provider-keys).

### Finding the source of a `400`

A `400` can come from our admission checks, from provider-specific translation, or from the provider itself. Check `error.code` and `error.param` before changing the body and retrying.

## Fields blocked on platform provider keys

When your request runs on the platform's own provider keys, we refuse it if it includes a field that:

- buys something we can't bill for yet, or
- asks the provider to store the conversation under our account.

The refusal happens before we hold any credit or call a provider.

| Type | Blocked fields |
| :-- | :-- |
| Service tier | Any `service_tier` other than the provider's standard one. Standard is `auto`, `default` or `on_demand` on chat completions, and `auto` or `default` on Responses. |
| Paid hosted tools | `web_search_options`, and any hosted tool the provider charges for per call: web search, web fetch, code execution, and Gemini grounding tools such as `google_search`. |
| Audio | Audio input (an `input_audio` part) and audio output (`audio`, or audio in `modalities`). |
| Long cache | A `cache_control` marker with a `1h` ttl. |
| Stored state | `store: true`. On `POST /v1/responses`, also `previous_response_id`, `conversation`, `item_reference` input items and `background: true`. |

Each refusal is a `400` with `code: null` and `param` set to the field name (never its value). The message tells you to remove the field or send the request on your own provider key.

**On your own provider key, all of these fields go through as you sent them**, because the provider bills and stores against your account. See [Bring your own key](/features/bring-your-own-key). Other fields still go through provider-specific translation and depend on what the provider supports.

## The refusals that are ours

Each of these is decided before any provider is called, and none of them charges
you anything.

**No model named.** The one field admission cannot do without.

```json 400
{
  "error": {
    "message": "You must provide a model parameter naming the model to call. It is read to work out what the request could cost before it is sent.",
    "type": "invalid_request_error",
    "param": "model",
    "code": null,
    "request_id": "REQUEST_ID"
  }
}
```

**A model field that is not a usable id.** Too long, or holding characters an id
cannot hold. The message states the shape it will accept:

```text
The model "..." is not a usable model id. A model field is at most 128
characters and may hold letters, digits and the characters . _ : / @ and -,
in either the "provider/model" or the "profile/{identifier}" form.
GET /v1/models lists the exact strings this key can call.
```

A well-formed id with no provider in front of it is a different refusal, `400`
with the code `model_id_not_pinned`. See [Models](/features/models).

**A prompt too large to hold credit against.** `400` with
`context_length_exceeded` and `param` set to `messages`. This is a refusal about
sizing the hold, and it happens before the model's own context window is ever
consulted, so it is not the same thing as a provider telling you the prompt does
not fit.

**No ceiling can be worked out.** `503` with `model_not_priceable`, when your
body names no output ceiling and the model publishes no maximum output either.
The message says what to do, and it is worth reading rather than retrying:

```text
This request names no maximum number of output tokens and no maximum output
length is published for "<model>", so the most it could cost cannot be worked
out. Send max_tokens and the request is admitted, because the published figure
is then not needed.
```

This is the one `model_not_priceable` that a retry does not fix. The others on
that code clear on their own. See [Errors](/api-reference/errors).

## `max_tokens` and what it holds

The credit held while a request runs is sized from an output ceiling, and the
ceiling is the smaller of two figures: the one you sent, and the model's own
published `max_output_tokens`.

| What you send | What is held against |
|---|---|
| `max_tokens` below the model's maximum | Your figure. |
| `max_tokens` above the model's maximum | The model's maximum, because the model cannot exceed it. |
| Neither field | The model's published maximum output. |

A body asking for more than one completion, with `n` or `best_of`, holds that many
output ceilings (the larger of the two when both are sent), because the provider bills each completion its own output. The
prompt is held once. A balance that cannot cover the larger hold is refused with the
ordinary `402`.

The hold is returned in full at settlement and you are charged for what the
request actually produced, so sending `max_tokens` never costs you the
difference. What it changes is how much of your account spend rate cap one
request occupies while it is in flight. See
[Rate limits and spend controls](/manage/spend-controls).

## The parameters a given model takes

`GET /v1/models/{id}` returns a `parameters` array for that model: the request
controls it accepts, with their bounds and defaults. It is served only on the
single-model call, never on the list, because a list is scanned and a detail is
read.

```json One entry
{
  "name": "temperature",
  "type": "number",
  "min_milli": 0,
  "max_milli": 2000,
  "default_milli": 1000,
  "enum_values": null,
  "sent_by_default": false,
  "note": "Higher values make the reply less predictable."
}
```

| Field | What it is |
|---|---|
| `name` | The parameter as it is spelled in a request body. |
| `type` | The shape of the control: `boolean`, `enum`, `integer`, `number` or `string`. |
| `min_milli`, `max_milli`, `default_milli` | The bound or default in thousandths of the parameter's own unit, or null where none is recorded. |
| `enum_values` | The closed set of values, for an `enum`, and null otherwise. |
| `sent_by_default` | Whether a client should send this parameter when nobody has touched it. |
| `note` | A short sentence about the parameter, or null. |

**The three bounds are in thousandths.** A temperature ceiling of two arrives as
`2000`, and a default of nought point seven as `700`. They are integers on
purpose: a bound that drifted in its last decimal place would be a contract about
nothing. Divide by a thousand before you show one to a person.

Two things this list is and is not. It is a description of a model, useful for
building a form or validating input before you spend a request finding out. It is
not a filter on the API: a parameter absent from the list is still forwarded if
you send it, and the provider still answers for it.

## What is not on this page

**A canonical list of every parameter the API accepts.** There is no such list,
because there is no allowlist. The parameters are OpenAI's, plus whatever a
provider takes, and the model detail above is the closest thing to a per-model
answer.

**Headers.** Nothing about how a request is served can be set from a header. See
[Headers](/api-reference/headers).
