The body of a chat completion uses OpenAI-compatible fields. Providers with a
different native API, including Vertex Gemini, receive translated fields. This
page describes admission checks and parameter metadata; the endpoint schema and
provider guide describe supported request controls.

## What is read

Admission reads two things out of your body, both to work out what the request
could cost before it is sent:

| Field | Why it is read |
|---|---|
| `model` | To find the provider, the rate, and whether we can serve it at all. |
| `max_tokens`, or `max_completion_tokens` | To size the credit held while the request runs. When both are present, the larger is used. |

Neither read changes the field, and the two fields answer differently when the
value cannot be made sense of.

A ceiling this cannot read falls back to being treated as absent rather than
being corrected, so credit is held at the model's published maximum output and
the provider answers for its own body. `model` has no such fallback: it is the
one field admission cannot proceed without, so a missing model and a model id in
a shape this does not accept are both refused here, before any provider is
called. Both refusals are in [The refusals that are ours](#the-refusals-that-are-ours)
below, and both name a `param`, which is how you tell them from the provider's.

## What is rewritten

Admission rewrites apply on every key, with additional restrictions on the platform's own provider
keys, [listed below](#the-fields-refused-on-the-platforms-own-provider-keys): an
omitted `store` on Responses is sent as `false`, and three routing fields a
reseller provider reads are removed from a chat body. All are named here because a body that arrives different
from the one you sent should never be something you discover from a provider's
error message.

**`model`, when you asked for a route rather than a model.** A request naming
`profile/{identifier}` or `unirouter/auto` is a request for a list of models
tried in order, so the body that reaches a provider carries the id of the model
being tried on that attempt. See [Routing profiles](/features/routing-profiles).

**`max_tokens`, when the provider's own API refuses a request without one.** Some
providers require the field. If your body carries neither `max_tokens` nor
`max_completion_tokens` and the provider is one of those, the field is added,
and the value used is the model's published `max_output_tokens`, which is the
figure credit was already being held against. An existing ceiling is not replaced
by this step. Provider-specific translation still applies afterwards.

**Vertex Gemini fields.** OpenAI-compatible fields are translated into Google's
request format. For example, `max_tokens` sets the output limit, `reasoning_effort`
selects a thinking level, and `modalities` and `image_config` control image output
on supported chat models. See [Gemini on Vertex](/features/vertex-gemini) for the
request and response shapes.

## What happens to everything else

For providers with a pass-through OpenAI-compatible API, additional parameters
can reach the provider unchanged. This is not a guarantee for native APIs such
as Vertex Gemini: only mapped fields reach its native request, and accepted
values depend on the model.

This cuts both ways, and the second half is the half worth planning for:

- **Published model metadata is not a request allowlist.** Absence from that list
  does not by itself cause an admission refusal.
- **A provider can refuse a parameter or value.** The API can also reject a value
  during provider-specific translation, before sending the native request.

  There is one exception, and it is a single value rather than a field: an empty
  or whitespace-only `reasoning_effort` is refused here with a `400`, `code`
  `invalid_value` and `param` set to `reasoning_effort`. It is the one value no
  provider accepts, so relaying it would spend a round trip to be told the same
  thing. Gemini translation also rejects `0` and `false`, and rejects `"minimal"`
  for models that disallow that thinking level, with `param: "reasoning_effort"`.
  Other values can still be refused by Google. See [Reasoning models](/features/reasoning).

  The other is a short list of fields refused on the platform's own provider
  keys and forwarded on yours, in
  [the next section](#the-fields-refused-on-the-platforms-own-provider-keys).

An HTTP `400` can therefore come from admission, provider-specific translation,
or the provider itself. Inspect `error.code` and `error.param` before deciding
whether changing the body will help.

## The fields refused on the platform's own provider keys

A request served on the platform's own provider keys is refused, before
anything is held and before any provider is called, when it carries a field
that buys something this platform cannot bill yet or asks the provider to keep
the conversation under our account:

- a `service_tier` other than the provider's standard one (`auto`, `default` or
  `on_demand` on chat completions, `auto` or `default` on Responses),
- `web_search_options`, or a hosted tool the provider charges for per call (web
  search, web fetch, code execution, and on a Gemini model a grounding tool such
  as `google_search`),
- audio in (an `input_audio` part) or out (`audio`, or audio in `modalities`),
- a `cache_control` marker with a `1h` ttl,
- `store: true`, and on `POST /v1/responses` also `previous_response_id`,
  `conversation`, an `item_reference` input item and `background: true`.

Each is a `400` with `code` `null` and `param` naming the field, never its value,
and the message says to remove it or send the request on your own provider key.
On `POST /v1/responses` an omitted `store` is sent to the provider as `false`.

**A request served on your own provider key keeps every one of them** and goes
out as you sent it, because the provider bills and stores it against your own
account. See [Bring your own key](/features/bring-your-own-key).

On chat completions, the routing fields `provider`, `models` and `transforms`,
which a reseller provider reads, are removed from the body rather than refused, so a client that
sends them keeps working and the model you named is the one you are charged for.
Other fields remain subject to provider-specific translation and support.

## The refusals that are ours

Each of these is decided before any provider is called, and none of them charges
you anything.

**No model named.** The one field admission cannot do without.

```json 400
{
  "error": {
    "message": "You must provide a model parameter naming the model to call. It is read to work out what the request could cost before it is sent.",
    "type": "invalid_request_error",
    "param": "model",
    "code": null,
    "request_id": "REQUEST_ID"
  }
}
```

**A model field that is not a usable id.** Too long, or holding characters an id
cannot hold. The message states the shape it will accept:

```text
The model "..." is not a usable model id. A model field is at most 128
characters and may hold letters, digits and the characters . _ : / @ and -,
in either the "provider/model" or the "profile/{identifier}" form.
GET /v1/models lists the exact strings this key can call.
```

A well-formed id with no provider in front of it is a different refusal, `400`
with the code `model_id_not_pinned`. See [Models](/features/models).

**A prompt too large to hold credit against.** `400` with
`context_length_exceeded` and `param` set to `messages`. This is a refusal about
sizing the hold, and it happens before the model's own context window is ever
consulted, so it is not the same thing as a provider telling you the prompt does
not fit.

**No ceiling can be worked out.** `503` with `model_not_priceable`, when your
body names no output ceiling and the model publishes no maximum output either.
The message says what to do, and it is worth reading rather than retrying:

```text
This request names no maximum number of output tokens and no maximum output
length is published for "<model>", so the most it could cost cannot be worked
out. Send max_tokens and the request is admitted, because the published figure
is then not needed.
```

This is the one `model_not_priceable` that a retry does not fix. The others on
that code clear on their own. See [Errors](/api-reference/errors).

## `max_tokens` and what it holds

The credit held while a request runs is sized from an output ceiling, and the
ceiling is the smaller of two figures: the one you sent, and the model's own
published `max_output_tokens`.

| What you send | What is held against |
|---|---|
| `max_tokens` below the model's maximum | Your figure. |
| `max_tokens` above the model's maximum | The model's maximum, because the model cannot exceed it. |
| Neither field | The model's published maximum output. |

A body asking for more than one completion, with `n` or `best_of`, holds that many
output ceilings (the larger of the two when both are sent), because the provider bills each completion its own output. The
prompt is held once. A balance that cannot cover the larger hold is refused with the
ordinary `402`.

The hold is returned in full at settlement and you are charged for what the
request actually produced, so sending `max_tokens` never costs you the
difference. What it changes is how much of your account spend rate cap one
request occupies while it is in flight. See
[Rate limits and spend controls](/manage/spend-controls).

## The parameters a given model takes

`GET /v1/models/{id}` returns `uniblock.parameters` for that model: recorded
request controls, with their bounds and defaults where known. It is served only on the
single-model call, never on the list, because a list is scanned and a detail is
read.

```json One entry
{
  "name": "temperature",
  "type": "number",
  "min_milli": 0,
  "max_milli": 2000,
  "default_milli": 1000,
  "enum_values": null,
  "sent_by_default": false,
  "note": "Higher values make the reply less predictable."
}
```

| Field | What it is |
|---|---|
| `name` | The parameter as it is spelled in a request body. |
| `type` | The shape of the control: `boolean`, `enum`, `integer`, `number` or `string`. |
| `min_milli`, `max_milli`, `default_milli` | The bound or default in thousandths of the parameter's own unit, or null where none is recorded. |
| `enum_values` | The closed set of values, for an `enum`, and null otherwise. |
| `sent_by_default` | Whether a client should send this parameter when nobody has touched it. |
| `note` | A short sentence about the parameter, or null. |

**The three bounds are in thousandths.** A temperature ceiling of two arrives as
`2000`, and a default of nought point seven as `700`. They are integers on
purpose: a bound that drifted in its last decimal place would be a contract about
nothing. Divide by a thousand before you show one to a person.

The separate `uniblock.supported_parameters` array contains parameter names from
publishable sources, after known refusals are removed. It is not a list of fields
proven by a successful call. Names such as `reasoning` describe a feature;
the request body can use a different spelling, such as `reasoning_effort`.

These arrays describe a model, not the complete request schema. Empty or missing
metadata does not mean every parameter is unsupported. Use the endpoint schema
for field names and types and the provider guide for model-specific limits.

## What is not on this page

**Every native provider parameter.** The endpoint reference documents the public
request schema. A native provider adding a new field does not establish that the
Hopscotch API already maps it.

**Headers.** Nothing about how a request is served can be set from a header. See
[Headers](/api-reference/headers).
