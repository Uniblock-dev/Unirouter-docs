By default Hopscotch keeps metadata about each request (time, model, token counts and cost), not the
prompt or response. **Capture** changes this for a key: its request bodies are stored, encrypted, for
you to read back, and charged for by the storage they hold. See
[Data and privacy](/manage/data-and-privacy).

<Note>
Capture is not yet available to production accounts. Turning it on is refused in production until
the opt-in path ships, so the steps below describe what the feature does where it is enabled, and
every step is gated.
</Note>

## Capture is off until you turn it on

Capture is set one key at a time. A new key starts with capture off, and a key with capture off
stores no bodies. You turn it on with a single switch beside the key.

Turning capture off is always allowed. It stops new bodies from being stored for that key, but
bodies already stored stay until you delete them or they expire. Turning it off is not a delete.

## What is stored for each captured request

Each captured request stores its prompt and response as one object, encrypted before it is written, with its metadata.
Responses returned in one piece are captured. Streamed responses are meant to be captured too, but
that is not shipped yet, so a streamed request stores its metadata and no body until it is.

## Viewing captured requests

Captured history is under Activity in the dashboard, newest first, narrowed by model, outcome, key,
dates or an exact request id. Opening a request shows its stored prompt and response. If a body cannot
be read, the request says so and still shows its metadata. There is no search over text. Captured
history is dashboard only; the `/v1` API does not read it.

## What storage costs

Storage is charged by the bytes held and the time they are held, from storage until deletion or
expiry. Once per calendar month, the charge is worked out from the stored bodies themselves. A missed day is picked up by the next run, and the same month is never charged twice. It appears on the balance ledger as its own line, not as a request charge. The price and this month's amount are shown
next to the capture switch. This page does not state a price.

If storage charges take an account's balance below zero, capture is switched off for its keys and the
owner is emailed. Requests keep working. See [Credits and billing](/manage/credits-and-billing).

## Expiry

Every stored body expires after a fixed retention window that is not configurable today, counted from the moment it was stored. A scheduled
job removes expired bodies, so one can remain briefly after expiry. Expired bodies stop being charged.

## Deleting captured history

You can delete captured history for one request, a time range, or everything in the workspace. The
request returns at once with a deletion receipt. The items vanish from history immediately, and their
bodies are removed from storage right after. The receipt stays pending until the removal is checked, and you can read it again by its id until then.

Deletion removes prompts and responses only, not metadata or balance changes. A deletion that does not
finish is raised as an alert, never left looking complete.

## Bringing your own bucket

Enterprise workspaces can connect a bucket they own on AWS S3 or Cloudflare R2, with a write-only
credential scoped to that bucket. A registration is accepted only after a test object is written, read,
listed and deleted. Once active, the capture destination can be set to that bucket, and deleting
history removes bodies there too. Setting the destination is not yet available in the dashboard.

Telemetry is streamed to your bucket, with bodies only for keys with capture on. A receipt verifying zero
retention on Hopscotch storage for a bucket destination is not yet shipped, so this page makes no such
claim. See [Zero data retention](/manage/zero-data-retention).

## The opposite choice: zero data retention

Capture off, the default, means no bodies are stored for that key. Zero data retention is a separate
control: it routes a request on our provider credentials only to providers whose published terms say
they keep nothing and train on nothing. Neither control turns the other on or off. See
[Zero data retention](/manage/zero-data-retention).
