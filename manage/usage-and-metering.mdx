Every request that reaches Hopscotch creates one usage record. The record holds facts about the request: when it ran, which model answered, what happened, how many tokens it used and what it cost. Your prompt and the model's reply are never in it.

Everything on this page is built from those records. The Usage screen adds them up, Activity lists them one by one, and every usage charge on your statement points back to one of them.

## What one record holds

| Field | What it is |
|---|---|
| `requestId` | Our id for the request. Quote this to us. |
| `occurredAt` | When the request started, `ISO 8601`. |
| `source` | The door it came through: `api` or `playground`. |
| `modelSlug` | The model called, as `provider/model`. |
| `providerSlug` | The provider that answered, or null where none did. |
| `outcome` | What became of the request. A closed set, listed below. |
| `servedOnOwnKey` | Whether the request ran on a provider key your workspace brought. |
| `promptTokens`, `completionTokens`, `totalTokens` | Input, output and their sum, or null where no count arrived. |
| `cacheReadTokens`, `cacheWriteTokens` | Input tokens read from or written to the provider's cache, or null where the provider reported no cache accounting. |
| `reasoningTokens` | Part of `completionTokens`, not additional to it, or null where none were reported. |
| `streamed` | Whether the reply was streamed. |
| `costMinor` | What the request charged, in integer minor units. Null means it was never priced. |
| `latencyMs` | The total time you waited, in milliseconds. |

Three things to know when you read these fields:

**A missing count shows as** `unknown`**.** If a count never reached us, the field is null and the screens show `unknown`. We never fill the gap with `0`. A real charge next to two zeros would look like a billing bug, so anything we didn't measure stays marked as unmeasured.

**This list is complete.** These fields are everything a customer-facing usage endpoint can return, and every one of those endpoints is checked against this list. Internal figures about our own performance and provider supply aren't included.

**Requests on your own provider key are metered too.** A request that runs on a provider key your workspace brought still gets a usage record, with `servedOnOwnKey` set to true. These requests are counted separately from the ones we served. See [Bring your own key](/features/bring-your-own-key).

## Outcomes

`outcome` tells you what happened to the request. The list of values is fixed, and we only add a new one when a feature needs it.

**Served**

| Outcome | What happened |
| :-- | :-- |
| `served` | The model answered. Charged. |

**Refused: charged nothing**

| Outcome | What happened |
| :-- | :-- |
| `refused_zero_balance` | Refused at admission because you didn't have enough credit available. |
| `refused_rate_capped` | Refused by your spend rate cap. |
| `refused_paused_by_owner` | The workspace owner has paused requests. |
| `refused_model_not_live` | The model couldn't be served. |
| `refused_not_permitted` | The caller wasn't allowed to make this request. |
| `refused_invalid_request` | The request couldn't be served as sent. |
| `refused_platform_unavailable` | No provider was tried. |

**Cancelled: charged nothing**

| Outcome | What happened |
| :-- | :-- |
| `customer_disconnected` | You closed the connection before the provider answered. |

**Stopped by a provider or a limit**

| Outcome | What happened |
| :-- | :-- |
| `provider_failed` | The provider answered with a failure. |
| `provider_rate_limited` | The provider turned the request away for rate reasons. |
| `terminated_zero_balance` | A stream was cut off when your credit ran out. |
| `terminated_deadline` | The request hit its deadline and was ended. |

**Charged, but final token counts never arrived**

For these five outcomes the token figures show `unknown`. The charge is whatever settled against the hold taken when the request was admitted.

| Outcome | What happened |
| :-- | :-- |
| `stream_incomplete` | The stream ended before the counts that close it arrived. |
| `usage_metadata_missing` | The reply came with no usage figures. |
| `usage_metadata_unreadable` | Usage figures arrived but couldn't be read. |
| `usage_not_reported_by_provider` | The provider served the request and reported no counts. |
| `rebuilt_from_ledger` | We rebuilt the record from the transaction the request created. |

## What is never recorded

We do not store your prompt or the model's reply, for API requests, playground runs or failed requests. The single request view says so in these words:

> No prompt and no response body was stored for this request; the figures here are everything that exists (we never store prompts).

That is why the playground has no history and no share link. See [Data and privacy](/manage/data-and-privacy).

## Usage

Usage is the sign-in screen. It reads one window at a time (24 hours, 7 days, 30 days, 90 days or 1 year) and shows:

- **Totals**: requests, served and not served, token counts including reasoning and cache reads and writes, and the summed cost.
- **The window immediately before it**, so a total reads as a change.
- **A series**, by hour on the 24 hour window and by day on the longer ones. An empty bucket carries a zero.
- **Breakdowns** by model, provider, key and member.
- **Your balance**, read from the one component allowed to compute it.

**Pace.** Usage shows your average daily spend for the selected range, how many days your balance will last at that rate, and the date it would run out. Pace is recalculated when you change the range. If you spend very little, it says "under a cent a day". If your balance would last more than ten years, it says so rather than showing a far-off date. The panel is hidden when there's nothing to project from, meaning no spend in the range or a zero balance.

**Freshness.** The screen shows two times: when the newest request in the range started, and when the figures were last read. Requests appear in Usage within 60 seconds of completing. That's the most we commit to, and most requests show up faster.

**Ranges longer than 90 days.** Usage records are kept for 90 days, so a 1-year range only shows what's still on record. Your statement goes back further, because transactions are never deleted.

## Activity: one row per request

Activity lists every request this workspace has made, newest first, one row per request. You get 25 rows a page, or 50 or 100 if you choose, and your browser remembers that choice.

Rows are sorted by time and then by request id. That keeps paging stable: a row won't appear on two pages or slip between them while you click through.

| Column | Shows |
|---|---|
| When | When the request started, in UTC. |
| Door | `api` or `playground`. |
| Model | The model asked for. |
| Served by | The provider that answered, or **nothing**. |
| Outcome | **served**, **provider error**, **refused**, **cancelled**, or **other** for a newer code. |
| Tokens | The total, or **unknown**. |
| Charge | The cost, or **unpriced** on an older row. |
| Took | Milliseconds. |
| Request id | The first eight characters, linking to the single request view. |

Reading the values:

- `backup `**next to the provider** means the answer came through a backup route. The model you asked for still answered. API callers see the same thing in the `x-hopscotch-served-via` header. See [Headers](https://docs.hopscotchlabs.ai/api-reference/headers.md).
- **Cancelled** means you closed the request before the provider answered. Nothing was charged. The "provider error" and "refused" filters leave cancelled rows out.
- **Refused and provider error rows** are drawn in their own color. Open the request to see the exact code.
- `unknown` means no count was reported. Showing it as `0` would make an outage look like a page of free requests.
- `unpriced` only appears on rows recorded before 2026-09-10. Since then every served request has a charge. When nothing more precise can be worked out, the charge is the amount you accepted at admission.
- **A refused request** shows a real charge of `0`. It's listed like any other row.

### Filters

| Filter | Choices | Default |
| :-- | :-- | :-- |
| Model | Any model, or one this workspace has called | Any model |
| Outcome | Any outcome, served, provider error or refused | Any outcome |
| From | Start date, included, in UTC | Empty |
| To | End date, excluded, in UTC | Empty |

- Filters combine, and each filtered view has its own URL you can bookmark.
- If the URL contains a value the screen can't read, the screen drops it and tells you which one.
- Shortcuts for the last day, week and month fill in the dates for you.
- There's no request id filter. To open one request, click its id in the row.

### Three ways to see no rows

The screen tells you which of these applies:

1. **Nothing has run in this workspace yet.** It invites you to send a first request.
2. **Your filters matched nothing.** It offers to clear them.
3. **Your date range goes back further than we keep records.** It tells you how long the retention window is.

## How to

### Look up one request

Every response carries the request id in two headers:

- `x-hopscotch-request-id`, which is ours
- `x-request-id`, which is the one the official OpenAI SDKs show on their error objects

Every error envelope repeats it as `request_id`. Include it whenever you ask us about a request, so we know exactly which one you mean.

To open a request, click its id in any Activity row. The single request view shows everything in the row, plus:

- whether the reply was streamed
- prompt, completion and total tokens
- when the figures were read, shown separately from when the request ran

A few cases to know about:

- **An id from another workspace and an id that never existed look the same.** Both find nothing, so a lookup can't reveal whether an id exists somewhere else.
- **A request older than 90 days** isn't found, and the screen names the retention window. Its charge is still on your statement.

### Reconcile a statement line with a request

A `usage` line on your statement carries our request id as its cause. That is the join.

<Steps>
  <Step title="Take the request id from the statement line">
    Every charge line names one.
  </Step>
  <Step title="Look it up in Activity">
    The single request view shows the model, the outcome, the token counts and the cost for that exact request.
  </Step>
  <Step title="Compare the figures">
    The charge on the usage record and the amount on the statement line match by request id, with no tolerance for a difference. If they disagree, that is a defect on our side. Quote the request id.
  </Step>
</Steps>

We also run this check ourselves. Usage figures and your balance are the same charges read two ways, and we match them by request id. Any difference at all alerts us, so you shouldn't have to be the one who finds it.

Two kinds of lines need a little more context:

- **A charge with a note.** Some lines say the counts weren't confirmed, the provider reported none, or the hold had expired by the time the charge settled.
- **A served request with no cost yet.** If token counts never arrived, the request settles against its hold, and the usage row can't show the amount yet. The window totals say how many of these requests they include, so you can tell the totals are incomplete.

## Who sees what

| Figures | Who can see them |
| :-- | :-- |
| Totals, breakdown by model, breakdown by provider | Every member, in full. |
| Breakdown by key, breakdown by member | Owners and admins see every line. Other members see the keys they're responsible for or named on, plus their own row. |

A per-member figure tells you whose key or account a request is tied to. It can't prove who actually sent it, because anyone holding an API key can use it.

## How long records are kept

> Usage records are kept for 90 days. The guaranteed minimum is 62 days, which is two full billing months.

Usage records are kept for 90 days. The job that deletes old records and the screens you read both use that same setting. It will never go below 62 days, so support can always look up a request from two full billing months back.

When a record passes 90 days, it's deleted. **The charge stays on your statement**, because transactions are never deleted. You can still explain your balance line by line.

If a date filter reaches past the window, the screen tells you, so you know why older rows are missing.

The Usage and Activity screens are live. The fields, outcomes and retention window on this page are what you see today.
