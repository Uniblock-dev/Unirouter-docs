This page lists what we promise and what we do not. Each promise below is something the product enforces, not a statement of intent.

## Your API keys

Because we store only a hash of each key, two things are true:

- **A database leak exposes no usable keys.** Nothing stored there can be sent as a bearer token.
- **Nobody can show you your key again, including us.** No support process, console screen or internal tool can read a key back, because we never stored the value it would need.

We refuse any key that is unknown, revoked or malformed. See [Authentication](/api-reference/authentication) for the response your client gets.

## Provider credentials

**You never hold a provider credential, and we never expose ours.** When you call a model, we substitute our own credential for the provider that serves it. You do not see it, you do not receive it, and nothing in a response lets you work it out.

A provider credential problem on our side is ours to fix, with nothing for you to change.

## Your prompts and replies

**We do not store the content of a request.** We record metadata about it: the model, the provider, the token counts, the cost, the latency and the outcome. The prompt and the response body are not stored, and that includes playground runs. See [Data and privacy](/manage/data-and-privacy).

## Invitations

An invitation link is stored only as a hash of its token, and an invitation is found by that hash. A database dump yields nothing that can be presented as a valid link.

An invitation works only for the email address it was sent to, expires after seven days, and re-checks the inviter's authority at the moment it is accepted. A link that matches nothing and a link that belongs to another address answer identically, so holding a session tells you nothing about who has been invited.

## Who can manage billing

We check permissions on our servers for every request, against your role at the moment the request arrives. If the dashboard hides a control from you, that's for convenience. The server would refuse the action anyway.

| Action | Owner | Admin | Developer | Viewer |
| --- | :-: | :-: | :-: | :-: |
| View the balance and statement | ✓ | ✓ | ✓ | ✓ |
| Buy credit and manage the card | ✓ | ✓ |  |  |
| Pause or resume requests | ✓ |  |  |  |
| Make someone an admin | ✓ |  |  |  |

**Ownership changes only through an explicit transfer.** The transfer demotes the outgoing owner in the same step, so a workspace always has exactly one owner.

**Admins can't create other admins.** If someone steals an admin session, they can't use it to promote another account that stays an admin after you end the session and change the password.

See [Workspaces and members](/manage/workspaces-and-members) for the full permission table.

## Your billing figures come from one place

Your balance, statement and usage figures all come from one accounting component, and each charge has exactly one record that explains it. There are no separate copies kept in sync by a background job, so the figures can't drift apart or disagree with each other.

Each charge records the model rates in effect when the request ran. A rate can't be changed once it has been used, so a later price change never alters what an earlier request cost.

## What we do not claim

Stated plainly:

- **No compliance certification.** No audit, certification or framework claim is made anywhere on this site, because none has been obtained.
- **No availability or latency promise.** There is no service level agreement and no published uptime or latency figure. Any number you may have seen elsewhere is a target of ours, not a commitment to you.
- **No revocation timing promise.** We do not publish how quickly a revoked key stops working everywhere, because it has not been measured on a deployed environment.
- **Nothing about provider-side handling.** What a provider does with a request we forwarded to it is governed by that provider.
- **No security contact yet.** This site does not yet name a channel for reporting a security problem. When one is published it will be on this page.

## Reporting something

If a request did something you can't explain, include its request id when you report it. Every response has one, whether it succeeded or failed, and it lets us find that exact request. The id helps far more than a description of what went wrong.
